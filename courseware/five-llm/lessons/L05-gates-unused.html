三道闸与刻意不用的回调

一个回合必须有界：请求有上限，工具有上限，时间有上限，人随时能取消。这一课看这些闸装在哪里，触发后谁看到什么；再看弈境为什么只挂了很少的回调。

原文：白皮书 §3.6–3.7、附录 C.2 + 代码现状勘误 §3.2阅读约 15 分钟含 2 个互动演示

学完本课，你能够：

  • 用接口面板比喻区分 L2 的读数口、断路器、净水器、插座、开关和定时器。
  • 说出三道闸的位置、上限和触发后的结果。
  • 区分技术超时和棋局超时。
  • 说出至少四个弈境刻意不用的回调，以及不用的理由。
  • 解释“权威越留在宿主，扩展挂的回调越少”。

01墙上的接口面板

先说结论：白皮书把 L2 比作墙上的接口面板。面板上的东西按能力分成几类。弈境只用了其中几类。

墙上的东西能做什么对应弈境用了吗
电表、水表的读数口只能看观察类事件：turn_start / message_* / tool_execution_*用了：L1 订阅 turn_start、tool_execution_end；L2 挂 turn_start
断路器、漏电保护、阀门能切断，跳闸后显示原因tool_call 拦截，理由作为工具结果回给模型用了：预算 16、取消与已提交守卫
净水器、稳压器、变压器改变流过的东西改写类钩子：context / tool_result 等没用
新装一个插座增加能力registerTool用了：8 个工具
墙上的开关住户一按就触发registerCommand（斜杠命令）没用
定时器、限流阀到点或到量就断预算闸：8 次请求、16 次工具调用、90 秒超时用了

接口里不放家电的逻辑。也就是说，L2 不放业务规则。

02三道闸，外加取消和棋钟

先说结论：三道闸保证一个回合有界。取消让人随时收回控制权。棋钟独立于这一切，由 L3 计算。

闸位置触发后
请求预算 8L1 订阅 turn_start 计数（pi-driver.ts:68-72）abort()；prompt() 返回后抛“已达到单回合 8 次 LLM 请求上限”；L3 显示错误，棋钟继续
工具预算 16L2 tool_call（gomoku.ts:82）返回 block，模型收到“单回合工具调用预算已耗尽”
技术超时 90 秒L1 setTimeout → abort()（pi-driver.ts:34）“LLM 思考超时（90 秒），可重试或换模型”；这和棋局超时是两回事
取消 / 新局 / 悔棋L3 invalidate() → controller.abort()L1 监听 port.signal 后 abort()；L2 的 ensureActive() 抛错；L3 的 valid() 拒绝迟到提交
棋钟L3 charge()，主进程 200 ms 心跳超时直接判负，与 Agent 状态无关；判负时 finish() 也会中止当前回合

L1 用一个 stopped() 函数统一报告停机原因（pi-driver.ts:32）：先看 port.signal 是否中止，再看是否超时。它在 Session 创建的各个阶段都调用一次。

本节核心句技术超时只结束这一次 Agent 尝试，可以重试。棋局超时是比赛结果，由 L3 判定。网络等待、工具调用、重试都在扣棋钟。
迟到的响应赢不了过期的棋钟port.commit 的第一行是 this.charge()（game-service.ts:175）。先结算时间，再判断回合是否有效。模型在时限后才提交，L3 先判负，提交随后遭拒。

03动手看：哪道闸先触发

下面的模拟器假设一个模型的行为。调滑块，看哪道闸先触发，以及触发后各方看到什么。

闸门压力测试：请求、工具、时间、取消、棋钟，谁先到
试三组：① 每次请求 4 个工具、第 5 次提交：第 17 次工具调用遭 block，提交永远进不去；② 每次请求 20 秒、第 6 次提交：90 秒技术超时先到；③ 剩余时间调到 30 秒：棋钟判负先到，它不看 Agent 在做什么。简化模型：每次请求耗时相同，工具执行不计时。提交是该次请求的最后一个工具。模型遭 block 后仍按原计划继续。剩余时间把基本用时和读秒合成一个数。数字只说明机制，不是测量结果。
补充：工具预算耗尽后为什么还会继续请求block 只拦住一次工具调用，不结束 run。模型收到“预算耗尽”的工具结果后，还可以再回复。所以工具预算耗尽后，最终通常由请求预算或技术超时收尾。这是课程作者按代码逻辑的推演。

04刻意没有使用的回调

先说结论：Pi 1.4.0 有很多能改变流程的插入点。弈境能改变流程的扩展回调只用了 tool_call 一个。其余的，宿主已经替它做了。

回调通常用途弈境为什么不需要
before_agent_start每次 run 前改写系统提示词或工具集系统提示词在创建 Session 之前由宿主装配，每手一个 Session
context每次请求前改写消息列表上下文本来就是新的，没有需要裁剪的历史
agent_end / agent_before_settle催促续跑（TillDone 的做法）停机条件由 L1 掌握：要么提交，要么预算或超时用尽；不希望模型被“劝”着继续
session_start / session_tree从会话历史恢复状态状态的权威在 L3，不在会话里
input、registerCommand用户输入与斜杠命令没有人类聊天输入，模型唯一的输入是宿主模板
before_provider_request改写发给 provider 的原始请求体不需要改写传输层
tool_result改写工具结果工具结果本来就由本扩展的 execute() 生成
turn_end要求再跑一个 turn不希望延长回合
状态和流程控制的权威越是留在宿主，扩展需要挂的回调就越少。白皮书 §3.6

“权威能留在宿主”是选择进程内 SDK 的直接结果（L03）。对照一下边牧：TillDone 是 TUI 扩展，状态在会话里。它要用 agent_end 督促续跑，用 input 复位督促闩锁，用 session_start 回放恢复状态。

白皮书过时白皮书 §3.6 说“five-llm 只用了其中的 tool_call 一个”。v2（提交 642481a）起，L2 另挂了观察类的 pi.on('turn_start')，给反馈打请求序号（gomoku.ts:26）。准确的说法是：能改流程的扩展回调只用 tool_call；观察类的 turn_start 用来记证据序号。上表列的回调仍然一个都没用。

06自测与速记

模型连续思考到 90 秒，L1 中止了回合。此时棋局会怎样？
技术超时只结束这一次 Agent 尝试。棋局超时由 L3 的棋钟判定。代码注释写明：请求错误、重试和取消从不重置比赛棋钟（game-service.ts:187）。
第 17 次工具调用会怎样？
预算闸在 L2 的 tool_call（gomoku.ts:82）。block 变成工具错误结果，run 不崩溃。
弈境为什么不需要 session_start 回放恢复状态？
白皮书 §3.6：状态的权威在 L3，不在会话里。每手一个内存 Session，用完 dispose()。
按代码现状，下面哪句最准确？
白皮书 v1.0 说只用了 tool_call。v2 起 L2 另挂了 pi.on('turn_start')（gomoku.ts:26）。
