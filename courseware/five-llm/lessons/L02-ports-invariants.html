L02 · 问题与全景

端口、单写者与 revision

L01 说“权威留在宿主”。这一课讲它怎样落到代码。L3 只认两个接口，棋谱只有一个写者，每个回合都带着版本号。多道检查拦下迟到、过期、重复的提交。

学完本课，你能够：

  • 说出 TurnPort 的四个成员，以及 AgentDriver 为什么只有一个方法。
  • 解释依赖倒置怎样让 L3 不知道 Pi 存在。
  • 列出六条不变量，并说出每条由哪一层、哪一行守护。
  • 对一次可疑提交，指出拦下它的层和模型收到的错误。

01L3 只认两个接口

先说结论：运行时链路不等于编译依赖。运行时，L3 调用 Agent；编译时，Agent 依赖 L3。L3 只定义两个接口，不 import Pi 或 Electron。

// 摘自 game-service.ts:7-14 // Dependency inversion: the domain knows this port, not Pi's implementation. export interface TurnPort { state: GameState; // 回合开始时的快照 signal: AbortSignal; // 取消信号 log(layer, text): void; // 写链路日志 commit(point, reason, decision?): void; // 唯一的写入通道 } export interface AgentDriver { run(port: TurnPort): Promise<void> }
端口
TurnPort

L3 每个回合发一个。它是本回合独有的“写入凭证”。L2 的工具只能通过 port.commit() 写棋谱。

驱动
AgentDriver

只有 run(port) 一个方法。L3 不关心对方是 Pi、替身，还是别的 Agent 框架。

  • L1 的 PiDriver implements AgentDriver。
  • L2 的 gomokuExtension(port) 接收同一个 TurnPort。
  • L1 和 L2 都 import 业务层的纯函数（engine、decision）。反方向的 import 一个都没有。
这就是典型的六边形（Ports & Adapters）架构：L1 和 L2 是“Agent 适配器”，L4 是“UI 与持久化适配器”。白皮书 §2.3
补充：port.state 是快照startAgent() 用 structuredClone 给端口一份快照（game-service.ts:168）。之后 L3 的真实状态继续变化，端口里的状态不变。所以 L2 拿快照里的 revision 和模型传来的 revision 比较，就能发现模型抄错了版本。

03六条不变量

先说结论：弈境的“权威”由六条不变量撑起来。每条都在代码里有固定的守护位置。

不变量守护位置机制
棋谱只有一个写者GameService所有写入都走 calculate()；渲染器只读快照（单写者）
过期回合不能落子game-service.ts:170 的 valid()五个条件：未取消、未终局、同一局、同一 revision、仍是当前控制器
迟到的响应赢不了已经超时的棋钟commit 第一行 this.charge()先结算时间，再判断回合是否有效
每回合只提交一次committed 标志（L2 和 L3 各一个）双重防护
坐标、占用、终局合法rules.ts 的 play()每次提交后从完整棋谱重放
规则是自由五子棋，无禁手RULESET = 'free-gomoku/v1'知识包只能建议，不能改写规则（自由五子棋）

commit 的完整顺序是这样的（game-service.ts:174-185）：

  1. this.charge()：先结算棋钟。超时就当场判负，并 invalidate()。
  2. valid() 为假或 committed 已为真：抛“过期、超时或重复的落子请求已拒绝”。
  3. 不是机器方回合：抛“不是机器方回合”。
  4. reason 为空或超过 600 字：抛“请提供不超过 600 字的简短落子理由”。
  5. play() 校验坐标和占用；通过后置 committed = true，记手记，calculate()。
白皮书过时白皮书 §2.2 写 L2 拥有“6 个工具”。代码现状是 8 个（gomoku.ts:11），新增 check_forcing_sequences 和 find_forcing_win。本课讲的不变量都没变：valid() 仍是五个条件，仍在 game-service.ts:170。

    05revision 贯穿四层

    先说结论：revision 是一个整数版本号。它从 L4 一直传到 L2，任何改变棋盘或回合有效性的操作都会让它变化。

    层revision 在这里做什么
    L4渲染器发 five:command {move, x, y, revision}，必须带上它看到的 revision
    L3humanMove 比对 revision，不符就报“棋盘已更新或本局已结束，请重新确认”；calculate() 和 invalidate() 让它加 1
    L1把 revision 写进用户提示词：“revision=17”
    L2validate_move、place_stone 等工具要求模型传 revision；不符就报“版本错误：当前 revision=17”

    哪些操作会改变 revision：

    • 人类落子、LLM 成功提交：calculate() 加 1。
    • 悔棋、取消、换模型、终局结算：invalidate() 加 1，并中止当前回合。
    • 新局、下一盘：先 invalidate()，再换成一局全新的状态。新局的 revision 从 0 开始，局 ID 也换了。
    本节核心句revision 回到 0 时，L3 仍然拒绝旧回合。因为 valid() 还比较局 ID 和当前控制器，不只比较 revision。

    悔棋有一个前提：比赛设置里启用了练习悔棋。默认的正式模式不允许悔棋（game-service.ts:134）。悔棋也不返还已用的时间和读秒次数。

    07自测与速记

    TurnPort 里哪个成员是跨层写入的唯一通道？
    L2 的工具只能通过 port.commit() 请求落子。L3 在 commit 里结算棋钟、检查 valid()、校验规则，然后才写入。
    冒烟测试换上一个替身 driver。哪一层的代码需要修改？
    依赖倒置：L3 只认 AgentDriver 接口。main.ts 在冒烟模式下注入替身，业务层一行不改。
    模型思考时机器方的棋钟耗尽，随后模型调用了 place_stone。为什么不会落子？
    “迟到的响应赢不了已经超时的棋钟”。commit 第一行是 this.charge()。技术超时（90 秒）是另一回事。
    新局让 revision 回到 0。一个旧回合恰好也带着 revision 0 提交。结果是什么？
    valid() 有五个条件，不只比较 revision。新局会 invalidate()，换局 ID，并新建控制器。
    模型把 revision 抄错了。错误文本发给了谁？
    place_stone 的 checkRevision 抛“版本错误：当前 revision=17”。Pi 把异常转成工具错误结果，模型据此修正。L07 会讲这条“错误即提示词”回路。

    速记表

    要点一句话
    两个接口TurnPort {state, signal, log, commit}；AgentDriver {run(port)}
    依赖方向L1、L2、L4 import L3；L3 不 import Pi 或 Electron
    组合根main.ts 注入 PiDriver、冒烟替身或失败替身
    commit 顺序charge → valid()/committed → 机器方回合 → reason ≤ 600 → play → calculate
    valid() 五条件未取消、未终局、同一局、同一 revision、仍是当前控制器
    revision 变化落子/提交经 calculate() 加 1；悔棋/取消/换模型/终局经 invalidate() 加 1；新局归 0 并换局 ID
