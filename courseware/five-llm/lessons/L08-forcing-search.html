连续冲四：反证、强杀与提交前反馈

白皮书 v1.0 之后，L3 又加了两个确定性工具和一道提交前门禁。这一课讲清三件事：它们从哪两局实战来；搜索算什么、不算什么；门禁怎样让关键反馈赶在落子之前进入上下文。

原文：L3 v2/v3 设计记录 + 代码现状勘误 §3.1–3.4阅读约 25 分钟含 3 个互动演示

学完本课，你能够：

  • 讲出 H7 与 G10 两个实战局面各暴露了什么缺口。
  • 说明连续冲四搜索怎样生成着法、何时停、证明长什么样。
  • 区分三种结果状态，解释为什么 not-found-within-budget 不等于安全。
  • 按 place_stone 的真实分支顺序，判断一次提交会落子还是返回 needsReview。
  • 说出这套机制验证了什么、没有证明什么。

01两局实战暴露的问题

先说结论：一步验证只看对手下一手能不能成五。它挡不住“连续逼着走”的杀法，也发现不了自己的强杀。两局真实对局各暴露了一个缺口。

v2 · 防守缺口
白 H7 遭到反杀

2026-10-30 人类胜局，第 21 手后白走 H7。H7 通过了一步验证。但黑可以 I7 → 白 H6 → 黑 M11 → 白 L10 → 黑 L11，得到 I11、N11 两个成五点。白棋曾保存的 H7 → 黑 I11 → 白 I8 有利分支，前提是黑棋配合。

v3 · 进攻缺口
白 G10 漏掉强杀

另一局白第 14 手前，白 G10 迫黑 G8，再白 J7 形成 F11、K6 两个成五点。白实际下了防守分更高的 H6。H6 和 G10 都通过了“对手反杀”检查，这个负结果比不出进攻质量。

后来黑棋超时不改变这个决策时刻，也不能将 H6 标为正确。own-forcing-win.md · 实战问题

两次修补走的是同一条落地链。每一环都是一个具体文件：

实战局面→原则 principle-evidence / tactics→剧本 midgame→技能 check-forcing-sequences / find-forcing-win→确定性工具 forcing.ts→候选级证据 candidateReview→回归测试 forcing-case / missed-win-case

两轮都没有引入第二个模型，也没有自动代下。工具只返回证据，不推荐落点。

02连续冲四是什么

先说结论：连续冲四是一串“每步都造四”的进攻。对手每步只能堵一个点，直到进攻方同时拥有两个成五点，或直接成五。

forcing.ts 的搜索按下面的规则走。全部计算只改棋盘副本，不碰真棋盘：

  1. 先看能否直接成五。进攻方有成五点，就以 five 结束。
  2. 再看对手的立即胜。防守方有 2 个以上成五点，这条线不成立。只有 1 个时，进攻方必须先占这一点。
  3. 生成造四着。扫描全部五格窗口。窗口里有 3 颗进攻子和 2 个空点，两个空点都是候选造四着。不用启发式排名剪枝。
  4. 造四后检查反杀。防守方此时能先成五，这一着作废。
  5. 沿唯一防点继续。只有 1 个成五点时，防守方只能堵它；其他应手下一手就输。所以只需递归这一个应手。
  6. 两个成五点即终点。防守方无立即胜，进攻方有 ≥ 2 个成五点，返回 two-winning-points。
本节核心句证明覆盖防守方的每一种应手，不是一条“对手配合”的单线。这正是 H7 案例里有利单线 H7 → I11 → I8 不算数的原因。
范围只搜连续冲四。不搜连续活三，不做完整博弈树，不求全局最佳落点。返回任意一条已证明的线路，不承诺最短或唯一。

04结果三态与预算

先说结论：只有 found-* 带证明。另外两种状态都不是安全证明。

状态含义不能怎样理解
found-forced-loss / found-forced-win找到连续冲四强制线路，带 proof不是唯一胜法，也不是最短或最优
not-found-within-budget指定深度内没找到不等于安全、必胜、必和或最优；不代表没有胜法
incomplete节点、时间、取消或棋钟预算不足不得声称检查已完成

搜索预算有三项。默认值和上限如下：

预算默认工具参数上限业务函数硬上限
造四延伸 maxAttackMoves31–44
节点 maxNodes6000≤ 600020000
时间 maxMs200 ms≤ 200500
  • 时间用单调时钟（performance.now()）。搜索开始时，以及约每 32 个节点，让出一次事件循环。这样取消、棋钟心跳和 IPC 都能运行。
  • 工具层还把 maxMs 压到“距丢失当前时段 − 2 秒”以内。时间紧迫（≤ 15 秒）时 maxMs 为 0，结果是 incomplete / clock-budget。
  • 截止后才找到的证明也报 incomplete，不冒充已完成。
  • 棋钟照常扣时。检查和反馈等待不暂停、不退款。

设计记录给出本机测量：H7 找到反证用 8 个节点，中位约 1.29 ms、p95 约 2.89 ms；I11 预算内未发现，13 个节点，中位约 1.30 ms、p95 约 2.55 ms。这是该局面的本机测量，不是所有局面的延迟保证。

05一个内核，两个用途

先说结论：反证和强杀用同一个搜索内核 searchContinuousFours。区别只在“谁是进攻方”。

对手反证（v2）

  • 入口 checkForcingSequences(position, candidate)。
  • 先用权威 play 落下候选，再以对手为进攻方搜索。
  • scope: opponent-continuous-four-only。
  • 工具 check_forcing_sequences，第 7 个工具。

己方强杀（v3）

  • 入口 findOwnForcingWin(position)。
  • 从当前行棋方开始搜索，返回 winningCandidate。
  • scope: own-continuous-four-only。
  • 工具 find_forcing_win，第 8 个工具。

v3 还把强杀搜索挂到观察上。条件是普通中盘：≥ 8 手、无立即胜负、不紧迫。模型第一次调用 analyze_position 或 evaluate_threats 时，L2 自动搜索。结果放进 ownForcingWin 字段。模型不必先想到 G10，也不必额外调用工具。

  • 同一回合缓存结果，重复观察不重算。
  • 自动搜索不占 16 次工具调用预算，但计算时间照常扣棋钟。
  • 显式零预算或浅层负结果，不能抑制这次默认搜索。
  • place_stone 在提交前还有一次兜底搜索（来源 pre-commit），不依赖提示词自觉。
白皮书过时白皮书 v1.0 写“6 个工具”“只挂了 tool_call 一个扩展事件”。现在是 8 个工具（gomoku.ts:11），L2 还挂了 pi.on('turn_start') 给反馈打请求序号（gomoku.ts:26）。工具调用上限 16、请求上限 8 都没变。

06提交前反馈门禁

先说结论：工具算出证据还不够。证据必须在模型下一次请求之前返回，模型才算“读过”。place_stone 用请求序号检查这一点；不满足就返回 accepted: false, needsReview: true，不落子，回合不结束。

按 gomoku.ts:188-242 的顺序，一次 place_stone 依次过这几关：

  1. 证据门禁。本回合没观察过局面，抛错。
  2. 是否需要审查。已下 ≥ 8 手、无立即胜负、不紧迫，才需要。需要审查但还没自动搜过强杀，先补搜一次（pre-commit）。
  3. 漏胜关。已证明有己方强杀，而且证明是本次请求才返回的，返回 unread-forced-win。选了别的点又没带 acknowledgeMissedWin，返回 missed-forced-win。
  4. 反证关。选的不是已读的证明起手时：没做对手反证，就当场补做并返回结果；反证是本次请求才返回的，也返回；结果是 found-forced-loss 或 incomplete 又没带 acknowledgeRisk，还是返回。
  5. 提交。调用 port.commit()，返回 accepted: true 和 terminate: true。

几条细则：

  • 同批预排不算已读。同一条模型回复里“检查 + 提交”，检查结果的请求序号等于当前序号，所以不算读过。代码不声称能看出模型是否理解了结果。
  • 两个确认参数分开。acknowledgeRisk 只确认对手反证的风险，不能绕过漏胜关。
  • 浅层负结果不抹正证明。同一候选有过 found-forced-loss，门禁优先取它，后来的浅层 not-found 不算数。
  • 不强迫额外等待的情形。开局、当前立即胜负、时间紧迫。一步警告仍然只提示，不阻止合法提交，避免在已经无解的局面里循环重试。
  • 只有 accepted: true 才结束回合。所有拒绝都不改真棋盘。
白皮书过时白皮书 §6.3 和 §7.2 第 8 条把“有风险的提交先返回 needs_review”写成改进建议。v2/v3 已经实现，字段名是 needsReview。但它只针对连续冲四：validateCandidate 的一步警告（如“对手下一手仍可成五”）仍然不阻止提交。

    08验证了什么，没验证什么

    先说结论：回归测试验证的是 Harness 的证据传递和门禁。它们不证明真实模型会下得更好。

    测试验证了什么
    forcing-caseH7 一步验证无警告，但强制线路成立；I11 拆掉这条杀法（只剩 N11 一个成五点）
    missed-win-case（7 项）G10 迫 G8：黑其他任何应手都输；G8 后 J7：黑任何应手都挡不住；八种旋转/镜像下同样成立
    forcing（12 项）、own-forcing（7 项）立即胜优先、对手反杀优先、跳四、长连、满盘和棋；零预算、节点/时间预算、取消、非法输入
    pi-integration真实 Pi SDK + 本地 SSE 替身：提交前反馈、改选、显式确认、同批不能冒充已读、浅负不抹正、紧迫跳过、迟到判负
    本地 SSE 测试验证真实 Pi Harness 的证据传递与门禁，不验证外部真实模型棋力。系统仍可能因预算、未覆盖的杀法或模型明确放弃已知胜法而漏胜；这不是全局必胜求解器。own-forcing-win.md · 验证与边界

    还要记住三条边界：

    • 失败、取消且未提交的尝试，不会持久化为落子手记。完整工具审计不在这一轮范围内。
    • “reviewed”只表示反馈跨过了请求边界，不证明模型理解了它。
    • 门禁不改写合法性、revision 或棋钟。迟到的提交照常判负。
    补充：这一课在全课中的位置L07 讲“把计算委派给确定性工具”。本课是它的最新一步：委派还不够，还要让结果在对的时机进入上下文。L09 讲这些证据怎样写进 candidateReview。

    09自测与速记

    对候选 I11 的反证返回 not-found-within-budget。下面哪种说法正确？
    负结果不等于安全、必胜或最优，也不覆盖连续活三。“没做完”对应的是 incomplete。
    模型在同一条回复里调用 check_forcing_sequences(I11) 和 place_stone(I11)。结果是什么？
    检查结果的请求序号等于当前序号，门禁判定“模型还没读过”。同批预排不算已读。
    观察结果显示己方有强杀，起手 G10。模型坚持下 H6，并带上 acknowledgeRisk: true。结果是什么？
    acknowledgeRisk 只确认对手反证风险，不能绕过漏胜关。需要 acknowledgeMissedWin: true，而且 H6 还要过对手反证关。工具从不自动替换落点。
    H7 局面里，延伸 2 次时没找到反证，延伸 3 次时找到了。模型先做 3 次的检查，再做一次 2 次的复查，然后不带确认参数提交 H7。结果是什么？
    较浅的负结果不能抹掉同一候选已有的正反证（gomoku.ts 用 findLast(... 'found-forced-loss') 优先取它）。坚持 H7 需要 acknowledgeRisk: true。
    下面哪项不是这套机制的目标？
    设计记录明确说：测试验证 Harness 的证据传递与门禁，不验证外部真实模型棋力。
