L07 · 业务层与上下文

上下文工程：用重建取代压缩

弈境关闭了 Pi 的自动压缩。它每手从权威棋谱重建全部上下文，并把计算和验证委派给确定性工具。这一课拆开模型每次请求实际看到的内容，再看这种做法的收益和代价。

原文：白皮书 §2.0、§6 + 代码现状勘误 §3.3、§3.7阅读约 20 分钟含 2 个互动演示

学完本课，你能够：

  • 列出模型每次请求看到的三块内容：系统提示词、工具定义、消息。
  • 说出用户提示词模板的六段，以及提示词藏身的另外三个地方。
  • 解释为什么对可完整序列化的状态，重建比压缩可靠，并说出它的代价。
  • 说出弈境把哪五类东西委派给了确定性代码。
  • 指出“策略警告进不了提交前上下文”这个缺口现在修到了哪一步。

01两条原则

先说结论：弈境的上下文设计落实了 2026-10-28 四层讨论定下的两条原则（白皮书 §2.0）。

原则 1
上下文管理是手段，业务语义是内容

每一个进入上下文的字段，都要能回答“它帮模型做哪个业务决策”。逐手评估只送 5 个字段；信号里每段都标 source。

原则 2
界面通道与上下文通道分离

界面数据直接来自 L3 状态，不经模型转述。冲突时以界面为准。模型的 reason 只是公开理由，从不作为状态来源。

L3 业务逻辑：决定什么信息进上下文、进多少、以什么形式进。白皮书 §2.0

02模型每次请求看到什么

模型每次请求看到三块内容。三块都由宿主控制。

系统提示词：整段替换，并屏蔽外来内容

PiDriver 把 systemPrompt 传给 DefaultResourceLoader（pi-driver.ts:52）。Pi 把它当作 customPrompt，整段替换默认的编码助手前言。再加上下面几项设置，系统提示词只剩弈境自己的内容，外加一个 <cwd> 段。

设置屏蔽了什么
appendSystemPromptOverride: () => []用户或项目的 APPEND_SYSTEM.md
noContextFiles: trueAGENTS.md / CLAUDE.md 等上下文文件
noSkills: truePi 技能清单段落
noExtensions: true + 只给内联工厂用户和项目扩展（它们可能改提示词）
noTools: 'builtin' + tools: GAME_TOOLSread / bash / edit / write 等编码工具

系统提示词怎样“切换”。弈境不在会话里切换，也不用 before_agent_start。它每手新建 Session，用新的剧本装配一份新的系统提示词。从一局棋看，提示词按局面切换：开局注入 opening，出现冲四换成 endgame，读秒紧张换成 time-pressure。

这有一个代价。回合中途时间可能突然变紧，evaluate_threats 会推荐另一个剧本。但系统提示词里的剧本全文不会更换。设计文档接受这一点。证据里记录回合开始时实际注入的剧本；模型需要时可以用 read_knowledge 读新剧本。

用户提示词模板：六段

模板在 pi-driver.ts:83-90，每手装配一次。所有内容都来自 L3 状态。

03提示词还藏在三个地方

先说结论：系统提示词和用户提示词之外，提示词还藏在工具描述、工具结果和错误里。Agent 系统很容易忽视这三处。

  1. 工具描述就是提示词。place_stone 的描述写着 “Commit ONE legal move after observing … accepted:true ends the run”。描述跟着工具定义进入每一次请求。
  2. 工具结果就是动态上下文。每个工具都返回 JSON，并附带 limitations、scope、hypothetical 等元数据。
  3. 错误就是纠正性提示词。“版本错误：当前 revision=17”“请先调用 analyze_position…”“该交叉点已有棋子”都是中文句子，写给模型看。Pi 把拦截和异常转成 isError 的工具结果，下一个 turn 它们进入上下文。这形成规则驱动的自我纠错回路。

缺口：策略警告不是错误

白皮书 §6.3 指出一个缺口。place_stone 提交前自动运行 validateCandidate。但“放弃了本手直接获胜点”“对手下一手仍可立即成五”这类警告不阻止提交。警告随 accepted: true 一起返回，而成功提交立刻结束回合。所以模型没先调用 validate_move 时，它在提交前看不到这些警告。

白皮书过时白皮书把“有风险的提交先返回 needs_review”写成改进建议。现在它已经实现，但只针对连续冲四。普通中盘里，缺少已读的对手反证，或放弃了已读的己方强杀，place_stone 都返回 accepted: false, needsReview: true，不落子（gomoku.ts:188-242）。L08 详讲。validateCandidate 的一步警告仍然不阻止提交，这部分缺口还在。

白皮书过时白皮书 §6.4 写“默认注入约 2.1k 字符，全量约 4.8k”。那是 13 个条目的 v1。现在 15 个条目全文合计 9707 字符；默认注入随剧本不同，在 2685 到 3535 字符之间（课程作者在提交 4f65e37 上实测 knowledgeContext()）。渐进披露省下的比例比白皮书写的更大。

05Compaction：用重建取代压缩

先说结论：对“状态可以完整序列化”的领域，压缩有损，重建无损。五子棋的完整状态就是一份棋谱。

手段位置说明
关闭自动压缩compaction: { enabled: false }（pi-driver.ts:43）Pi 的 _checkCompaction 直接返回，不生成摘要
每手重建每手新建内存 Session + dispose()历史对话从不累积；“记忆”是权威棋谱，每次全量注入
装配时摘要逐手评估只留 5 个字段完整候选集留在本地棋谱
只注入一份剧本knowledgeContext(playbook)4 份剧本只注入 1 份
硬上限8 次请求 / 16 次工具调用一个回合内上下文的增长有界
完整上下文来自业务棋谱，不依赖可能被压缩或残留的对话状态。弈境 README（白皮书 §6.4 引用）

这也回答了四层讨论稿的一个问题。讨论稿担心“受保护内容”会在裁剪或压缩后消失。它核对出：context 钩子的返回值只影响单次请求，不写回会话。所以受保护内容必须每次从 L3 状态重新注入。弈境把这条结论推到了极致：它根本不保留历史，整个上下文都是受保护内容。因此它连 context 钩子都不需要。

代价有三条：

  • 每手重发完整系统提示词。弈境还设了 cacheWarming: 'off'（pi-driver.ts:44）。白皮书建议把稳定部分放前面、可变的剧本放最后，以利用 provider 的前缀缓存（§7.2 第 3 条）。
  • 单手上下文随棋局线性增长。棋谱和逐手摘要都是 O(手数)。上一个演示里，80 手时这两段约 8.3k 字符，仍远小于模型窗口。
  • 候选集重复两次。它同时出现在 analysis.candidates 和 signals.heuristics.candidates 里。这是可以省掉的冗余（§7.2 第 2 条）。

06动手看：压缩还是重建

同一局棋走到第 N 手。左边假设用一个长会话加自动压缩，右边是弈境的每手重建。拖动手数，打开“中途悔过棋”，看两边能否答对四个问题。

对照：长会话 + 压缩，和每手重建
当前手数 N 36

假设：长会话 + 自动压缩（弈境没有这样做）

    弈境：每手重建

      把 N 拖过 20。左边第一次压缩后，早期棋步只剩大意，完整棋谱无法复原。打开“悔棋”：左边的历史里还留着已撤回的棋步。右边每手都从权威棋谱重建，四个问题都答对；代价是每手重发系统提示词。简化模型，不是原文实验。左边的参数是示意：每手对话约增长 1200 字符，窗口预算 24000 字符，所以每 20 手压缩一次；压缩后旧棋步只留一句摘要。右边的大小沿用上一个演示的近似公式（midgame）。“能否答对”只表示上下文里有没有可靠依据，不预测具体模型的表现。

      07Delegation 与四层分布

      先说结论：弈境的委派是委派给确定性代码，不是委派给子 Agent。它把“需要放进上下文的东西”换成“可以调用的能力”。

      委派对象原本要放进上下文的现在
      知识（渐进披露）15 个条目全文，约 9.7k 字符入口 + 索引 + 1 份剧本，约 2.7k–3.5k 字符；其余用 read_knowledge(id) 按需取
      计算让模型自己数连子、找威胁analyze_position / evaluate_threats 返回确定性结果
      推演让模型在脑中走几步simulate_moves 在副本上走 1–6 手；check_forcing_sequences / find_forcing_win 做有界连续冲四搜索
      验证让模型自检合法性和一步杀validate_move / place_stone 内置 validateCandidate
      裁决让模型判断规则rules.ts，模型无法参与

      重构文档把“多模型 review-agent / 并行 simulate-agent”列为暂缓项。理由是费用、棋钟预算和故障传播都还没评估。棋钟每秒都在扣，所以这个取舍合理。确定性扫描几乎零延迟。一次子 Agent 调用至少多一次网络往返。按 v2 设计记录，H7 局面的反证检查本机中位约 1.29 ms（只是该局面的测量）。

      Prompt 与 Context 在四层中的分布

      层对提示词与上下文的贡献
      L1系统提示词装配与屏蔽；用户提示词模板；thinking 级别 low；请求预算
      L2工具名、描述与 schema；工具结果 JSON；拦截与错误文本；terminate 语义；needsReview 反馈
      L3知识包文本；剧本路由；结构化信号契约；规则错误文本；连续冲四证据；DecisionTrace
      L4不参与提示词；只展示公开理由与日志，不索取思维链

      08自测与速记

      弈境的系统提示词怎样随局面“切换”？
      白皮书 §6.2：不在会话里切换，也不用 before_agent_start。每手一个新 Session，用新剧本装配。回合中途不换。
      为什么弈境关闭了 Pi 的自动压缩？
      白皮书 §6.4：对状态可以完整序列化的领域，重建是无损的。每手从权威棋谱全量注入，历史对话从不累积。
      按代码现状，validateCandidate 发出“对手下一手仍可立即成五”的警告时，会怎样？
      needsReview 只针对连续冲四的反证和己方强杀。一步警告仍不阻止合法提交，这部分缺口还在（勘误 §3.3）。
      按代码现状，默认注入的知识大约多少字符？
      课程作者实测 knowledgeContext()：opening 2685、midgame 3535、endgame 2761、time-pressure 2779 字符。15 条全文合计 9707 字符。白皮书的 2.1k / 4.8k 是 v1 的数字。
