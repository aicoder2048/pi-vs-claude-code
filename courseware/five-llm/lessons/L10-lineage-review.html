pstack 血统、实战复盘与改进

弈境的知识层借鉴了 pstack，但把路由权、验证时机和状态所有权收回到宿主。这一课先对照“提案”和“实现”，再读一局真实对局的复盘。最后按代码现状盘点风险和下一步。

原文：白皮书 §4.6–4.8、§7–8、附录 C + 重构说明 + 勘误阅读约 20 分钟含 3 个互动演示

学完本课，你能够：

  • 说出实现怎样处理每条 Grok 改造提案（采纳、改造、否决或暂缓），以及理由。
  • 用一句话说准弈境与 pstack 的关系。
  • 说出一局 40 手实战复盘能说明什么、不能说明什么。
  • 画出自我改进闭环，指出现在缺哪几步。
  • 按代码现状判断白皮书 §7.2 的 11 条风险是否仍成立。

03准确的定位

pstack 模式弈境的对应物差异
poteto-mode 编排入口gomoku-coach + turnGuidance()剧本由代码选定，不由模型自主选择
原则索引5 条原则的简短索引常驻上下文全文按需读取
任务剧本4 个棋局情景剧本共用同一套四步 ID，不是可变的依赖图
专项技能领域技能（现在 5 项）只是说明文档，执行者是工具
prove it works提交前候选验证 + 每手全谱重放一步验证；v2/v3 另加有界的连续冲四检查
共享 todo / 决策 artifact内存闭包状态 + notes[].decision只在成功提交时生成摘要
子 Agent、多模型审查无只有一个主棋手
模型角色配置文件单一模型 + 固定预算没有 reviewer / judge 角色
本节核心句弈境是一个受 pstack 启发、由宿主显式管理的领域知识包与工具服务层，不是完整的 pstack 式多 Agent 技能平台。

04一局 40 手的复盘

复盘读取的是 2026-10-30 保存的一局真实对局：人类执黑，openai-codex/gpt-6.1-sol 执白，第 40 手 M9 连五获胜。20 手模型落子都带 gomoku-knowledge/v1 决策记录。复盘用当时的规则引擎全谱重放，40 份逐手评估和 20 份候选验证都与保存值一致。

项目观察结果
剧本分布opening 4、midgame 13、endgame 3（第 24、36、40 手）、time-pressure 0
observe 证据20 回合最后一次观察都是 evaluate_threats
变化试算15 回合 done，5 回合 skipped
提交前验证20 回合全部合法，warnings 全部为空
额外知识全文只有入口和选中剧本，没有额外读取任何原则或技能
与启发式排名15 手选第 1 名；5 手选第 2、6、8、9 名，L3 没有把它们强制换成榜首
耗时平均 10.5 秒 / 手，最短 3.8 秒，最长 19.4 秒；终局时模型还剩约 390 秒基本用时
  • 第 24 手 L8：事实驱动防守。黑方唯一的立即成五点是 L8，路由选中 endgame，模型直接封堵。
  • 第 38 手 J6：进攻判断。双方都没有立即胜点，路由仍是 midgame。J6 形成两端都能成五的四子。这说明 endgame 的触发含义是“当前已经有一手成五点”。
  • 第 40 手 M9：直接获胜优先。endgame 剧本直接取下胜点，没有多余试算。

能说明

剧本编排、结构化信号和受控工具确实在起作用。模型的行动与信号相符，低分但合法的选择也受到尊重。

不能说明

没有对照组，不能把胜局归因于知识包。没有走到时间剧本，没有额外技能读取和失败纠错的样本。技能“可用”，不等于模型读取或遵循了它。

05自我改进：线头与闭环

先说结论：线头已经埋好。复盘用人工方式跑通了闭环的第一圈。自动化的环还没有闭合。

线头对自我改进的价值
版本化知识包 KNOWLEDGE_VERSION能把对局结果归因到某个知识版本
每手 DecisionTrace能分析“读了某技能的回合是否更少漏防”
每手 evaluations + 结果 outcome能对比启发式第一候选与模型实际选择
userData/records/*.json 原子保存天然的离线数据集
测试中的 Pi SSE 替身可以扩展成固定局面的回归评测

白皮书列出缺少的四件事：可观测性不足；没有读取历史记录的分析器；没有评测基准；没有把结论写回知识包的通道。

点下面闭环图的每一步，看它在代码现状里有没有。

闭环图：每一步现在有没有
依次点 6 个方框。v2 和 v3 各自把“局面库 → 回归测试 → 人工修订”走了一圈，但“离线分析器”仍是人工。闭环图依据白皮书 §4.8 的建议图重画（白皮书标注“建议，未实现”）。每步的现状由课程作者按勘误和 v2/v3 设计记录判断。
白皮书过时白皮书只记录了闭环的第一圈。之后 v2 与 v3 本身就是“实战复盘 → 人工修订知识包与工具 → 回归测试”又转了两圈：
  • v2 来自 2026-10-30 的人类胜局：白棋下 H7 后，黑棋用连续冲四反杀。它固化为 tests/forcing-case.test.ts，知识包升到 v2。
  • v3 来自白棋在 G10 有强杀却下了 H6，固化为 tests/fixtures/missed-white-win-g10.json 与 missed-win-case.test.ts，知识包升到 v3。
它们仍是人工闭环：没有代码读回 records/ 做统计，也没有跨模型、跨版本的评测基准。
保留人工审阅知识包会进入每一手的系统提示词。自动改写它的风险（提示词漂移、对单一模型过拟合）高于收益。所以白皮书主张修订这一步保留人工。

    07结论与房子比喻

    白皮书把弈境的答案归纳成三句话：

    Harness
    权威留在宿主

    Agent 通过端口提交。运行链路自上而下，依赖方向指向中心的业务层。

    Loop
    一手棋一次 settle

    在工具准备阶段挂钩子；用 terminate 加 abort 保证提交即停；三道闸保证有界。

    Context
    每手重建

    宿主选剧本，模型在白名单里按需取知识，计算、推演、验证委派给确定性工具。

    白皮书提出的下一步三件事：补可观测性；把关键警告放到提交之前；显示已记录的 DecisionTrace。按代码现状，第二件对连续冲四已经做到（L08）。第一、三件仍待做。

    用房子比喻复习四层

    层比喻弈境里对应
    L0公用事业公司：水电煤气，按套餐或按量计费模型提供商
    L1入户管网：建筑商铺好，住户不改Pi 双循环：run 内循环 + settle 外循环
    L2标准接口面板：插座、电表、断路器ExtensionAPI：tool_call 拦截、registerTool
    L3家电本体：保险丝、程序、说明书规则、信号、剧本与技能、GameService
    L4控制与显示终端：墙上触屏Electron 桌面

    一句话区分：菜谱是方法，按钮是接口，电机是实现。比喻也有失效处：真实房子里水电是“笨”的；在 Agent Harness 里，做决策的是 L0 送来的模型，L3 反而负责把关和提供事实。

    08自测与全课速记

    Grok 提案里的 principle-double-three-forbidden（双三禁手原则）实现为什么否决了它？
    RULESET = free-gomoku/v1，无禁手。principle-rules 明确写“无禁手”。重构说明把 Renju 禁手列为需要独立设计的新规则集。
    Grok 提议“落子之后用分析和试算自检”。实现改成了什么？
    落子后自检要多一次模型请求、多扣一段棋钟，而且已经无法撤回。所以 verify 放到提交之前。
    40 手复盘里，模型赢了。这能证明知识包提升了棋力吗？
    白皮书 §4.7：能说明编排与信号在起作用，不能把胜局归因于知识包。
    按代码现状，白皮书 §7.2 第 8 条“策略警告在提交前不反馈给模型”是什么状态？
    v2/v3 让连续冲四反证和己方强杀在提交前跨过请求边界返回给模型。validateCandidate 的一步警告仍随 accepted: true 一起返回。
