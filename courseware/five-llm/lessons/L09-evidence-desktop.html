L09 · 证据、界面与复盘

决策证据与桌面层

模型每落一子，L2 就写一份决策证据。L4 把权威状态画到桌面上。这一课看证据记了什么、能保证到哪一级，以及桌面层怎样隔离、推送和保存。

原文：白皮书 §4.5、§5 + L3 v2/v3 设计记录 + 勘误阅读约 20 分钟含 3 个互动演示

学完本课，你能够：

  • 列出 DecisionTrace 的字段，说明它只记什么、不记什么。
  • 说出 candidateReview 的作用和 coverage 的五个取值。
  • 用四种保证强度判断一份证据能证明什么。
  • 说出弈境渲染器的隔离措施和 IPC 校验。
  • 解释心跳快照为什么不会让渲染器 5 Hz 重建整个界面，也不会触发写盘。

01DecisionTrace：只记工具证据

先说结论：DecisionTrace 只记录工具实际执行产生的证据。它不记录、也不索取模型的私有推理。

place_stone 成功时，L2 组装一份 DecisionTrace。它经 port.commit 写进 notes[].decision，然后随棋谱原子保存。字段定义在 decision.ts:70-79：

字段内容说明
version知识包版本现在写 gomoku-knowledge/v3；类型兼容 v1、v2 的历史手记
revision提交时的业务版本号v2 新增
playbook回合开始时注入的剧本如实记录，不假装中途换过剧本
knowledgeRead入口 + 剧本，再追加 read_knowledge 读过的 ID由代码登记，不靠模型自述
stepsobserve / compare / verify / commit 各为 done 或 skipped，附 evidence 文字跳过时写明原因
validation提交前的一步反击扫描scope: one-ply-only
candidateReview候选级证据（可选）v2 新增，见下一节
“执行了检查”“记录了证据”“模型看见了反馈”“模型据此修正”是四种不同强度的保证，当前的 DecisionTrace 可靠地提供了前两种。白皮书 §4.5
本节核心句compare: done 只表示“确实调用过试算或反证”。它不推断模型在内部比较过候选。

02candidateReview 与 coverage

白皮书 v1.0 的实战复盘指出证据粒度有四个问题。v2 用 candidateReview（版本 candidate-review/v1）补了一部分。它把证据绑定到具体候选上。

字段记录什么
candidate最终提交的候选
simulations[]全部成功试算：ID、revision、起始候选、完整坐标分支、终局与末端即时信号
forcingChecks[]全部对手反证：候选、来源、结果、返回时的请求序号。另记是否在提交前已返回先前请求、是否明确确认风险
ownWinChecks[]全部己方强杀搜索：来源 observe / explicit-tool / pre-commit，结果与证明（v3）
finalCandidateSimulationIds、finalCandidateCheckIds哪些试算和反证属于最终候选，区分“探索别的候选”和“审查最终候选”
forcingReviewreviewed / not-checked / skipped-time-pressure / not-required-immediate
ownWinReview、declinedProvenWin己方强杀是否跨过请求边界返回；是否在读过证明后显式选了别的点（v3）
coverage最终候选的审查范围，五个取值之一
coverage
single-line-only

最终候选只有单条试算线。

coverage
bounded-refutation

最终候选有已返回先前请求的完整有界反证。

coverage
incomplete-refutation

反证没有完成（节点、时间、棋钟预算不足）。

coverage
own-forcing-proof

最终选的就是已读过的己方强杀起手。别的候选不能冒领这条证明。

第五个取值是 not-compared：没有任何比较证据。

白皮书过时白皮书 §4.5 的字段表只有 version、playbook、knowledgeRead、steps、validation 五项。代码现状新增了 revision 和 candidateReview（decision.ts:56-79）。§4.5 列的四个粒度问题现在是这样：
  • 第 1 条（覆盖式变量）：部分修复。试算已是绑定候选的数组；但 observed 仍是覆盖式字符串（gomoku.ts:95）。
  • 第 2 条（compare: done 含义偏弱）：部分修复。done 改为“最终候选有成功试算，或有完整有界反证，或选了已证明的强杀起手”。
  • 第 3 条（knowledgeRead 混合注入与读取）：仍成立。
  • 第 4 条（失败、取消、超时的回合不留记录）：仍成立。内存日志只留 80 条，也不导出。

下面的演示列出几种回合。每种回合给出 DecisionTrace 里会记下的片段，并逐级判断四种保证是否成立。先选一个场景。

证据强度梯子：这份记录能证明到第几级
场景： 
    
    
    
    
    
    
    先看“读过反证后改选”，再看“同批预排”。两者最后都记成 reviewed：L2 用请求序号拒绝了同批的提交，迫使反馈跨过请求边界。再看“超时失败的回合”：四级全部落空，因为失败回合不进 notes。简化模型：JSON 是按 decision.ts 类型手写的示意片段，省略了大部分字段；坐标 H7、I11、G10、H6 借用 v2/v3 设计记录里的实战局面，请求序号是例子。第 4 级永远只能“推断”：记录能说明行为与反馈一致，不能证明因果。
    
  
    
  
    补充：为什么第 3 级靠请求序号同一条模型回复里的工具调用是一次性排好的。模型排下“检查 + 提交”时，还没看到检查结果。所以 L2 用 turn_start 数出的请求序号判断：反馈必须在更早的请求里返回，才算“看见”。L08 讲门禁本身。
    

    



    
  
    04从 TUI 到 Electron
    
  
    Pi 1.4.0 原生的 L4 是终端界面。扩展用 setFooter、setWidget、setStatus、ui.custom() 往终端里画。终端画不了图片、Canvas 棋盘和动画。
    
  
    2026-10-28 的讨论稿列了三条路线：A 在扩展里起本地网页；B 用 RPC 或 SDK 宿主驱动 Pi，再接 Web 前端；C 在 B 外面套 Electron。当时的判断是先做 A 验证需求。实际第二天就直接走了 C。
    
  
    迁移到 Electron，三件事发生了根本变化：
    
  
    
    
    变化 1
    L4 独立成进程
    扩展里不再有绘制代码。界面数据全部来自 L3 快照。“界面通道与上下文通道分离”到这里才在进程级别成立。
    
    
    变化 2
    权威搬到宿主
    TUI 扩展把状态写进会话树再回放恢复。弈境的权威在主进程的 GameService，Pi 会话每手用完即弃。
    
    
    变化 3
    领域原生的表达
    Canvas 木纹棋盘、棋钟、手记、回看滑块、背景音乐，终端里都做不到。
    
  
    
  
    对照边牧边牧也从 TUI 走到 Electron，但它用 RPC 子进程原样复用 TUI 扩展。弈境用进程内 SDK。L03 讲这两种接入方式的取舍。
    

    



    
  
    05进程模型与安全边界
    
  
    先说结论：权威在主进程。主进程严格隔离渲染器，渲染器只能通过 4 个方法和主进程说话。
    
  
    
    
    措施位置作用
    
    
    GameService 与 200 ms 心跳在主进程main.ts:149浏览器会节流后台渲染器的定时器，主进程不受影响
    
    
    contextIsolation: true、sandbox: true、nodeIntegration: falsemain.ts:122渲染器隔离
    
    
    禁止新窗口、禁止导航、拒绝所有权限请求main.ts:124-126渲染器不能跳到别处，不能拿摄像头等权限
    
    
    preload 只暴露 bootstrap、command、exportRecord、onStatepreload.ts通道 five:bootstrap / five:command / five:export / five:state
    
    
    trusted(event) + validCommand()main.ts:40、:43IPC 双重校验：发送方是主窗口主框架；命令形状合法
    
    
    模型认证只在主进程的 Pi ModelRuntimepi-driver.tsAPI key 不进渲染器
    
  
    
  
    本节核心句渲染器不能提交 LLM 落子，也不能改权威棋谱。它只发命令、收快照。
    

    



    
  
    06动手看：心跳与去抖
    
  
    主进程每 200 ms 心跳一次，也就是每秒 5 份快照。每份快照都推给渲染器，也交给自动保存。两处都要避免“每份快照都干全套活”。
    
  
      
    
    • 渲染器：apply() 比较 id、revision、status、error 和最后一条日志。全部相同就只重画棋钟（渲染去抖）。同一局 revision 回退的快照直接丢弃，防止乱序。
      • 
    
    • 自动保存：保存键是 id / revision / 双方剩余读秒次数（main.ts:83）。键不变就不写盘，所以心跳不触发写盘。写入是串行的原子保存。
      • 
  
    

  
    
    
    
      
    心跳模拟：同一串快照，两种渲染策略各做了多少活
    
      
    
    
    
    
      
    渲染策略：
        
          
          
        
      
    
      
    
        
        
        
        
      
    
      
    
    
    
    
    
    
    把时长拉到 120 秒，切换两种策略。全量重绘时 Canvas 重建次数等于快照数；实际做法只在状态真变时重建。写盘次数两种策略都一样，因为它只看保存键。简化模型：假设每次落子、每条新日志、每次丢失读秒各让一份快照“真变化”，彼此不重叠；落子同时让 revision +1。乱序快照指同一局 revision 比当前小的快照。数字只说明机制。
    
  
    

    



    
  
    07可视化了什么，还缺什么
    
  
    
    
    已可视化来源
    
    
    棋盘、手数、末手、胜利连线、前三候选提示position、analysis.candidates
    
    
    状态卡：轮到你 / 正在思考 / 请求已停止 / 等待重试 / 结束 / 回看status
    
    
    双方棋钟与读秒clock（心跳驱动）
    
    
    LLM 的公开落子理由、用时、模型notes[].reason 等
    
    
    黑白局势条blackScore / whiteScore
    
    
    四层链路日志（最近 24 条，带层标签）logs
    
  
    
  
    白皮书过时白皮书 §5.5 没写这些 L4 新功能：
    
      
      
    • 最新一手的青色光晕，加棋盘下方的说明文字“青色光晕 · 最近落子：…”（app.ts:92、:155-156）。光晕常驻，不是一闪而过，所以长回合之后仍看得见。
      • 
      
    • 胜负庆祝（celebration.ts）：人类赢放彩纸，机器赢下较安静的墨雨。
      • 
      
    • 结束音效：人类赢是上行琶音，机器赢是下行乐句（audio.ts）。背景音乐是本地两首 mp3。
      • 
    
    
  
    
  
    缺口仍在：DecisionTrace 没有显示在界面上（勘误确认）。剧本、读过的知识、四步状态、候选审查都已持久化，界面只显示 reason 一句话。边牧早期的“助手卡片大多为空”是同一类问题。数据已经有了，只是没有按“任务 → 步骤 → 证据”呈现。
    

  
    
    
    
      
    庆祝判定：这份快照会不会放庆祝，放多少
    
    
    
    
    
      
    先猜，再点事件：
        
          
          
          
          
          
          
          
          
        
      
    
      
    
    
    
    
    
    
    依次点前四个事件：都不放庆祝。规则只认“同一局、上一份快照还没结束、这一份刚分出胜负”。演示用 JS 照抄了 newRoundWinner() 的判定（celebration.ts:7-9）。粒子数取自 particles()。“回看”只改渲染器的 viewing，不产生新快照，演示把它当作同一份快照处理。
    
  
    

  
    持久化
    
  
    每盘一个 userData/records/<game-id>.json，格式 five-llm/v1。内容有棋谱、逐手评估、手记（含可选的 decision）、棋钟和比分。写入是串行的“临时文件 + rename”。退出时最多等 3 秒排队中的写入（main.ts:155）。v2/v3 没有改记录格式，只在手记里加了可选字段，旧记录继续有效。
    

    



    
  
    08自测与速记
    
  
    
    
    某手棋的 DecisionTrace 写着 compare: done。它能说明什么？
    
    
    
    
    DecisionTrace 只记工具实际产生的证据。done 不推断模型的内部推理，也不证明最优。
    
  
    
  
    
    
    按代码现状，下面哪个粒度问题仍然完全成立？
    
    
    
    
    前三项已修或部分修复：试算是绑定候选的数组，compare 条件改严，revision 已加入。失败回合仍不进 notes，内存日志只留 80 条且不导出。
    
  
    
  
    
    
    心跳每秒推 5 份快照。为什么不会每秒写 5 次盘？
    
    
    
    
    main.ts:83 拼保存键，键变了才写。心跳只推进棋钟时间，不改这三个量。
    
  
    
  
    
    
    启动时加载了一盘人类已赢的棋。界面会放彩纸吗？
    
    
    
    
    newRoundWinner() 要求同一局的上一份快照还没结束。启动加载没有上一份，所以不放庆祝，也不放结束音效。
