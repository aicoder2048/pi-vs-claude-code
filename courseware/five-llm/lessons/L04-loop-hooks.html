L04 · 循环工程

双循环接入点：提交即停

一手棋只跑一次 settle。真正的工作发生在 run 内循环里。这一课逐个看弈境在循环上挂了哪些点，以及“落子成功就立刻停”是怎样做到的。

原文：白皮书 §3.1–3.5 + 代码现状勘误 §3.1–3.2阅读约 20 分钟含 2 个互动演示

学完本课，你能够：

  • 说出 settle 外循环和 run 内循环在 Pi 源码里的位置。
  • 解释弈境为什么 N ∈ {1, 2}、M ≤ 8、K ≤ 16。
  • 按 Who / Where / When 说出七个接入点。
  • 解释为什么 terminate 不够，还要 abort()，以及为什么不 await。
  • 区分 L1 订阅的 turn_start 和 L2 挂的 turn_start。

01Pi 1.4.0 的双循环

先说结论：Pi 有两层循环。外层叫 settle，管“停没停稳”。内层叫 run，管“模型—工具”往返。弈境几乎只用内层。

外层
settle 外循环

一次 prompt() 对应一次 settle。一个 run 结束后，如果有重试、压缩、排队消息或续跑请求，就再起一个 run。停稳时发出 agent_settled。

内层
run 内循环

反复执行 turn。一个 turn = turn_start → LLM 流式回复 → 执行这条回复里的工具 → turn_end。

白皮书给出了源码定位。下表的行号指 Pi 1.4.0 在 node_modules 下的编译产物。

02弈境怎样用双循环

先说结论：一手棋 = 一个内存 Session = 一次 settle。外循环几乎只转一圈，内循环才是主战场。

白皮书用三个符号计数：N = run 数，M = turn 数（即 LLM 请求数），K = 工具调用数。

run 数
N ∈ {1, 2}

压缩关闭，没有续跑处理器，也没有排队消息。只有 retry: { maxRetries: 1 } 能再起一个 run。

LLM 请求数
M ≤ 8

L1 数 turn_start。第 9 次就 abort()，请求不会发出。

工具调用数
K ≤ 16

L2 的 tool_call 钩子计数。第 17 次返回 block。

  • Session 由 SessionManager.inMemory() 创建。finally 里 session.dispose()（pi-driver.ts:97）。回合之间没有对话残留。
  • 压缩关闭：compaction: { enabled: false }（pi-driver.ts:43）。
  • 8 个工具都声明 executionMode: 'sequential'。Pi 因此走顺序执行分支。
本节核心句settle 外循环只是外壳。弈境的约束全部落在 run 内循环上：请求数、工具数、提交即停。

04扩展工厂、tool_call 与八个工具

① 扩展工厂：每手装配一次

gomokuExtension(port, playbook) 返回一个 扩展工厂 pi => { … }。L1 把它放进 extensionFactories（pi-driver.ts:51），再 await resourceLoader.reload()。这是内联工厂，不经文件路径导入。

工厂体内声明本回合的闭包状态（gomoku.ts:23-26）：

  • calls：工具调用计数。committed：是否已提交。observed：最后一次观察。modelTurn：请求序号（v2 新增）。
  • simulations、forcingChecks、ownWinChecks：绑定候选的证据数组（v2/v3 新增）。
  • knowledgeRead：初始化为入口和选中剧本。

为什么每手一个工厂？状态天然按回合隔离。port 是本回合独有的写入凭证，旧回合的工具写不到新棋盘上。加载后 L1 还要检查：扩展没有错误；活跃工具都在 GAME_TOOLS 里，并且包含 place_stone（pi-driver.ts:64-67）。否则报“工具隔离校验失败”。

② tool_call：执行之前的闸

pi.on('tool_call', event => {
  ensureActive();                       // 已取消或已提交时直接抛错
  if (++calls > 16) return { block: true, reason: '单回合工具调用预算已耗尽' };
  … port.log(…)                        // 链路日志
  return undefined;                     // 放行
});
  • Pi 先用 TypeBox 校验参数，再调这个钩子。所以 event.input 已经通过 schema，坐标一定是 0–14 的整数。
  • 返回 block 或直接抛错，都变成一条 isError 的工具结果回到上下文。整个 run 不会崩溃。这是错误即提示词的基础。
  • 预算放在这里，不放在 execute 里。理由有两条：不存在的工具、参数非法的调用也该计数；拦截发生在执行之前，没有副作用。

05动手看：terminate 为什么不够

先说结论：Pi 只在同一批工具全部返回 terminate: true 时才停（白皮书引 agent-loop.js:471-472）。模型在一条回复里同时调 place_stone 和别的工具时，别的工具会“否决”这个 terminate。Pi 还会再请求一次模型。

弈境分两步解决（pi-driver.ts:73-80，提交判断在 :79）：

  1. L1 订阅 tool_execution_end。看到 place_stone 成功且 accepted === true，就设 committed = true 并 abort()。
  2. abort() 让 signal 进入中止状态。顺序批次在下一个工具前检查到它，跳过剩余工具。settle 外循环也不再续跑。

    先选 [analyze_position, place_stone] 和“只靠 terminate”：place_stone 排在最后也停不下来，因为同批的 analyze_position 没有 terminate。再切到“terminate + abort”，多出的请求消失。最后把结果改成 needsReview：没有落子，也不该停，模型要在下一次请求里读反馈。简化模型：按白皮书 §3.4④⑥ 与 pi-driver.ts、gomoku.ts 的逻辑推演。“只靠 terminate”是假设的对照，不是弈境的做法。假设本回合已经观察过（“抛错”选项除外），请求计数从这条回复算起。
    为什么 abort 不 awaitabort() 用 void session.abort() 调用（pi-driver.ts:33）。事件回调在 run 内部执行，而 abort() 会等待空闲。在这里 await，run 就永远等不到空闲，形成死锁。prompt() 返回后，if (committed) return 把“自己发起的中止”当作成功（pi-driver.ts:91）。白皮书记录：这个缺陷是在回归测试“混合批次”时发现的。
    双重防护就算 abort 没赶上，L2 还有一道：committed 为真后，ensureActive() 对任何工具都抛“本回合已经落子”。L3 的 valid() 也拒绝第二次提交。

    06两个 turn_start，两件事

    先说结论：弈境在两个地方监听 turn_start。它们目的不同，不能互相替代。

    ⑤ L1：session.subscribe

    • 位置 pi-driver.ts:68-72。
    • 每个 turn 恰好一次 LLM 请求，所以 turn_start 是天然的请求计数器。
    • requests > 8 时 abort()。中止发生在第 9 次请求真正发出之前。

    管预算。宿主订阅，只观察，靠 abort 生效。

    ⑤′ L2：pi.on('turn_start')

    • 位置 gomoku.ts:26：modelTurn++。
    • 每条反证、强杀证据都记下 returnedOnTurn: modelTurn。
    • place_stone 比较序号：反馈必须在更早的请求里返回，才算模型读过。

    管证据。扩展事件，用来打时间戳。

    为什么要序号？模型可以在一条回复里预先排好 [check_forcing_sequences, place_stone]。两个工具执行时，模型还没看到检查结果。序号相同，place_stone 就返回 needsReview，不落子。

    白皮书过时白皮书 §3.4② 说 tool_call 是“唯一挂上的扩展事件”，§3.6 说“只用了 tool_call 一个”。v2（提交 642481a）起，L2 另挂了 turn_start（gomoku.ts:26）。能改变流程的扩展回调仍然只有 tool_call。

      08自测与速记

      模型在一条回复里调用 [analyze_position, place_stone]，提交成功。如果弈境只靠 terminate: true，会发生什么？
      Pi 的规则是同批全部返回 terminate 才终止。analyze_position 不返回 terminate，所以会多一次请求，多扣一段棋钟。弈境用 L1 的 abort() 补上。
      L1 的事件回调里为什么写 void session.abort()，而不是 await？
      abort() 会等待空闲。回调本身在 run 里执行，等空闲就等不到。白皮书 §3.4④⑥。
      L2 的 pi.on('turn_start') 用来做什么？
      数请求、第 9 次中止是 L1 的 session.subscribe。L2 的 modelTurn 是 v2 新增的证据序号（gomoku.ts:26）。
      弈境一次 settle 里最多有几个 run？为什么？
      压缩关闭、没有续跑处理器、没有排队消息，只有 maxRetries: 1。所以 N ∈ {1, 2}。弈境不督促。
