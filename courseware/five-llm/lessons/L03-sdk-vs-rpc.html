Pi SDK 接入：每手一个 Session

弈境不启动 pi 子进程。它在 Electron 主进程里直接调用 Pi 的 TypeScript SDK，每手棋创建一个全新的内存 Session。这一课讲为什么这样选，以及 PiDriver 怎样把 Pi 收窄成一个只会下棋的引擎。

原文：白皮书 §5.2、§6.2、§2.0 末段 + 代码现状勘误阅读约 18 分钟含 2 个互动演示

学完本课，你能够：

  • 列出驱动 Pi 的四种方式，说出哪两种能支撑桌面应用。
  • 用一句话说出 RPC 和 SDK 的选型原则，并说出 SDK 的三项代价。
  • 按顺序讲出 PiDriver.run() 创建 Session 的五步。
  • 说出每个屏蔽项挡住了什么，以及哪两项共同挡住 read / bash。
  • 解释弈境怎样不用 before_agent_start 就“切换”系统提示词。

01驱动 Pi 的四种方式

先说结论：程序可以用四种方式驱动 Pi。前两种是一次性的，适合脚本。能支撑交互式桌面应用的只有 RPC 和 SDK。

方式形态适合
print跑一次，打印最终回答脚本、一次性任务
JSON 事件流跑一次，把事件逐行输出脚本、子 agent
RPC独立子进程，stdin / stdout 收发 JSONL长时间交互；边牧
TypeScript SDKcreateAgentSession()，嵌进宿主进程把 Pi 当引擎；弈境、楚河

同一个仓库里两种选择都有，可以直接对照：

// 边牧：apps/tilldone/src/rpc.ts:25 + config.ts:26 spawn(piBin, ["--mode", "rpc", "--no-extensions", "--model", model, "-e", extension, …]) // 弈境：apps/five-llm/src/agent/pi-driver.ts:58 createAgentSession({ resourceLoader, tools: GAME_TOOLS, noTools: 'builtin', sessionManager: SessionManager.inMemory(cwd), … })

02RPC 还是 SDK

要“复用一个现成的 Pi 体验”就用 RPC；要“把 Pi 当成引擎嵌进一个领域应用”就用 SDK。白皮书 §5.2

边牧：给现成扩展换一张脸

  • 扩展 extensions/tilldone 原样加载，一行不改。
  • 一个长寿命子进程，对话持续累积。
  • 业务状态只能从事件流推断：reduce(state, rpcRecord)。
  • 扩展的 TUI 绘制代码在桌面上失效。

进程隔离：Pi 崩溃不拖垮界面。

弈境：把 Pi 当引擎

  • 内联工厂 gomokuExtension(port, playbook)，为本应用量身定做，不落盘。
  • 每手一个内存 Session，用完 dispose()。
  • 工具里同步调用 port.commit()，直接走业务层的权威校验。
  • 不用扩展 UI；界面状态全部来自 GameState。

同进程：错误以异常形式回到 GameService。

弈境需要的五项能力，只有 SDK 能干净地提供：

  1. 每手一个全新 Session，从权威棋谱重建上下文。RPC 要做到这一点，就得每手重启进程。
  2. 系统提示词按局面切换。SDK 在创建 Session 时整段传入。
  3. 工具隔离：只开放领域工具，并在运行时校验。
  4. 同步、权威的提交：place_stone 在同一进程里调用 port.commit()，校验当场完成，错误当场返回给模型。
  5. 精细的循环控制：订阅 turn_start 实现请求预算，订阅 tool_execution_end 实现提交即停。
SDK 的代价Pi 和应用同处一个进程，失去进程级的故障隔离。Pi 的版本锁进应用依赖（package.json 锁定 1.4.0），升级要随应用发版。内存 Session 不落盘，失败回合的完整过程无法事后恢复。
白皮书过时白皮书 §5.2 第 3 项写“只开放 6 个领域工具”。代码现状是 8 个（gomoku.ts:11 的 GAME_TOOLS），新增 check_forcing_sequences 和 find_forcing_win。选型理由不变。
层的边界跟着进程边界走边牧的 README 把“Electron 运行时 + 外部 pi 可执行文件”整体算作 L1。弈境把 Pi 扩展算作 L2，把 PiDriver 算作 L1。原因是：用 RPC 时 Pi 是一个黑盒进程；用 SDK 时 Pi 的扩展面直接向宿主敞开（白皮书 §5.2 末段、§2.0 末段）。

04PiDriver 怎样创建一个 Session

先说结论：PiDriver.run() 每手做五步。前四步把 Pi 收窄成一个只会下棋的引擎，第五步保证用完即弃。

  1. 设置（pi-driver.ts:42-45）：SettingsManager.inMemory 关闭压缩，重试最多 1 次，关闭 cacheWarming、安装遥测和统计。
  2. 资源加载器（:46-54）：DefaultResourceLoader 设五个屏蔽项，只传一个内联扩展工厂。宿主装配的 systemPrompt 整段替换默认前言。
  3. 加载与检查（:55-57）：await resourceLoader.reload() 执行扩展工厂；扩展有加载错误就抛“五子棋扩展加载失败”。
  4. 创建 Session（:58-67）：createAgentSession({ thinkingLevel: 'low', tools: GAME_TOOLS, noTools: 'builtin', sessionManager: SessionManager.inMemory(cwd) })，然后做工具隔离校验。
  5. 释放（:97）：finally 里清定时器、取消订阅、session.dispose()。回合之间没有任何对话残留。
本节核心句每手一个内存 Session，只调一次 prompt()，用完 dispose()。Pi 的会话从来不是状态的权威。
补充：为什么还要工具隔离校验tools: GAME_TOOLS 本身就是白名单（Pi SDK 的说明：给出列表时只启用匹配的工具）。noTools: 'builtin' 又关掉内置工具。两项配置之后，PiDriver 仍在运行时检查一遍：活跃工具必须都在 GAME_TOOLS 里，而且包含 place_stone。配置写错时，这一步让回合在发出任何请求之前失败。

05动手看：屏蔽项开关台

Pi 默认是一个编码助手。它会自动读入用户和项目的很多东西。弈境用下面这些设置把它们全部挡在外面（白皮书 §6.2）：

设置屏蔽了什么
systemPrompt（customPrompt）Pi 默认的编码助手前言，以及默认的 tools、rules、docs 段
appendSystemPromptOverride: () => []用户或项目的 APPEND_SYSTEM.md
noContextFiles: trueAGENTS.md / CLAUDE.md 等上下文文件
noSkills: truePi 技能清单段落
noExtensions: true + 只给内联工厂用户 / 项目扩展（它们可能修改提示词）
noTools: 'builtin' + tools: GAME_TOOLSread / bash / edit / write 等编码工具

另外两项 noPromptTemplates、noThemes 关掉斜杠模板和主题。弈境没有人类在聊天，用不到它们。

下面的开关台从弈境的真实配置出发。取消勾选一项，看三件事：系统提示词多出哪一段，工具清单多出什么，工具隔离校验能否通过。

屏蔽项开关台：拿掉一项，Pi 会混进来什么
先只取消 noTools: 'builtin'：read / bash 不会回来，因为 tools 白名单还在。再取消 tools: GAME_TOOLS：编码工具回来了，工具隔离校验失败，本回合不发请求。再只取消 noSkills：技能段也不出现，因为 Pi 只在 read 或 bash 可用时才列技能。简化模型：段落名和出现条件依据 Pi 1.4.0 的 system-prompt.js（buildSystemPromptSections）与 sdk.d.ts 的 tools / noTools 说明。“若存在”表示只有本机真的有这些文件或扩展时才会混入；文字内容是示意。
仍然留下的一段无论怎样设置，Pi 都会附加一个 <cwd> 段。弈境的 cwd 是 userData 目录，所以本机路径会进入系统提示词。白皮书 §7.2 第 4 条把它列为风险：与任务无关，还暴露本机路径。

06提示词怎样“按局面切换”

先说结论：弈境不在会话里切换系统提示词，也不用 before_agent_start。它每手新建 Session，用新选出的剧本装配一份新的系统提示词。

  1. turnGuidance(port.state, Date.now()) 按局面选一个剧本：opening、midgame、endgame 或 time-pressure。
  2. systemPrompt = SYSTEM + knowledgeContext(playbook)：固定的棋手角色，加上知识包入口、索引和选中剧本的全文。
  3. 这份提示词只属于这一手的 Session。下一手重新选、重新装配。

所以从一局棋的角度看，系统提示词是按局面切换的。开局注入 opening；出现立即成五点时换成 endgame；读秒紧张时换成 time-pressure。

原文接受的代价回合中途，evaluate_threats 可能返回一个不同的推荐剧本（比如时间突然变紧）。系统提示词里的剧本全文不会随之更换。设计文档接受这一点：证据里记录回合开始时实际注入的剧本；模型需要时，可以用 read_knowledge 读取新剧本的全文（白皮书 §6.2）。L06、L07 会展开剧本路由和上下文装配。

07自测与速记

下面哪项需求最能说明弈境为什么不用 RPC？
界面需求两种方式都能做。同步、权威的提交是 SDK 独有的：经过 RPC，这一步要变成跨进程的请求 / 应答。
只把 noTools: 'builtin' 去掉，保留 tools: GAME_TOOLS。read / bash 会出现吗？
Pi SDK 的说明：给出 tools 时只启用匹配的工具。noTools: 'builtin' 是第二道保险，工具隔离校验是第三道。
弈境怎样在一局棋里“切换”系统提示词？
白皮书 §6.2：没有在会话里切换，也没有用 before_agent_start。每手一个 Session，每个 Session 一份按局面装配的提示词。
下面哪一项是 SDK 方案的代价，而不是 RPC 方案的代价？
其余三项都是 RPC 方案的特点。SDK 的代价：同进程无故障隔离、Pi 版本随应用发版、内存 Session 不落盘。

要点一句话

SDK 五项能力每手新 Session、提示词切换、工具隔离、同步提交、精细循环控制
