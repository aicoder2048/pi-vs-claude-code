# L3 v2：候选的连续先手反证与提交前反馈

> 本文记录 v2 对手反证及当时验证结果。v3 已增加第八个工具、己方强杀自动发现与漏胜反馈；当前增量契约见 [己方强杀发现](own-forcing-win.md)。对手反证接口保持兼容。

## 从实战到实现

2026-10-30 人类胜局第 21 手后，白棋 H7 通过一步验证，却允许黑棋 I7 → 白 H6 → 黑 M11 → 白 L10 → 黑 L11，形成 I11/N11 两个成五点。白棋曾保存的 H7 → 黑 I11 → 白 I8 有利分支，并不能保证黑棋配合。

本轮将复盘落实为：Principles 的证据边界 → midgame 剧本的触发动作 → check-forcing-sequences 技能 → 确定性计算工具 → 候选级证据 → 回归测试。不引入额外模型或自动落子。

## 计算契约

实现：`src/business/forcing.ts`，入口 `checkForcingSequences(position, candidate, options)`。

- 用权威 `play` 校验候选，后续仅修改内部副本。
- 检查候选之后，对手是否能以连续冲四强制获胜。自己的候选若直接成五/和棋，不继续搜索。
- 全部五格窗口用于即时成五和造四着法生成；不使用局部候选排名剪枝。任何造四着法都必须来自“三颗进攻子 + 两个空点”的五格窗口。
- 先检查进攻方是否能直接成五；否则进攻方若面临唯一成五威胁，必须先占该点；面对多个立即败点且无立即胜，则不能声称有连续冲四证明。
- 每次造四后检查防守方能否先成五。防守方无立即胜且仅有一个必须防点时，其余应手均会下一手输棋，所以只需继续该唯一防点。
- 防守方无立即胜而进攻方有至少两个成五点，即形成强制获胜的终点。返回交替线路和终点成五点，不只是任意单线模拟。

结果：

| status | 含义 |
|---|---|
| `found-forced-loss` | 对该候选找到连续冲四强制反证，有 proof |
| `not-found-within-budget` | 指定深度内未找到这种反证，不是安全证明 |
| `incomplete` | 节点、时间、取消或棋钟预算不足，不得称检查完成 |

默认最多三次造威胁延伸、6000 节点、200ms；深度可指定 1..4。业务函数硬上限为 20000 节点/500ms，模型工具只允许更小的 6000/200。最终直接成五的收尾可出现在延伸末端；proof 也可止于无法同时封堵的多个成五点。

时间使用单调时钟；搜索开始及每约 32 节点让出事件循环，允许取消、棋钟和 IPC 通知运行。进入读秒/包干压力范围（距丢失当前时段 ≤15 秒）不启动额外搜索，显式调用返回 `incomplete/clock-budget`。棋钟由 GameService 在提交时重新扣算，不因工具检查或复核反馈暂停、退款。

范围仅连续冲四，不含完整博弈树、连续活三或全局最佳落点。负结果不代表必胜、必和、安全或最优。

## 工具与提交契约

新增受限工具 `check_forcing_sequences`，输入 x/y/revision 及可选预算。它只返回候选证据，不返回推荐着法，不修改真棋盘。总工具数由 6 增至 7，请求上限 8、工具调用上限 16 不变。

普通中盘（至少已落八手、没有当前即时胜负、时间非紧迫）的最终候选需经过提交前反馈：

```text
observe
→ check_forcing_sequences(candidate)
→ 工具结果返回当前请求
→ 下一次模型请求：改选、继续探索，或提交
```

若直接调用 place_stone 而没有该候选的检查，它自动检查并返回：

```text
accepted: false
needsReview: true
check: { ...候选级反证... }
```

此时没有落子，也没有结束 Agent Loop。只有 `accepted:true` 才终止同批后续工具和下一次请求。

- 同一模型请求内预先安排“检查 + 提交”不算已读反馈；用 turn_start 序号确保结果至少已返回先前请求。不声称能观察模型是否理解结果。
- 发现败势或检查未完成时，重新提交同候选还需显式 `acknowledgeRisk:true`；仍不改写合法性、revision 或棋钟。
- 后续较浅的负检查不能覆盖同 revision/候选已有的正反证；保留全部检查并要求确认已知败势。
- 开局、当前立即胜负和时间紧迫时，不强迫额外检查或等待一轮。一步警告仍允许合法提交，避免在已经无解的局面循环重试。
- 未观察本回合事实仍不能提交；取消、过期和非法检查不产生成功证据。

## 知识与证据版本

知识包升级为 `gomoku-knowledge/v2`。保留 5 条原则、4 个剧本，专项技能增至 4 项。仍由宿主明确注入入口、简短索引和选中剧本，其他全文按 ID 白名单读取，不启用 Pi 通用技能/文件读取。

`notes[].decision.candidateReview` 为可选字段，版本 `candidate-review/v1`：

- 所有成功试算：ID、revision、起始候选、完整坐标分支、终局及末端即时信号，不再只覆盖保存最后一条。
- 所有成功反证检查：ID、revision、候选、来源、状态、预算、节点、耗时、证明、返回请求序号、是否在提交前已返回先前请求、是否明确确认风险。
- 最终候选对应的 simulation/check IDs，区分探索其他候选和审查最终候选。
- `coverage`：`single-line-only`、`bounded-refutation`、`incomplete-refutation`、`not-compared`。
- `forcingReview`：已返回先前请求、未检查、因时间跳过或即时胜负不要求检查。

四步 ID 仍为 observe/compare/verify/commit。compare=done 表示最终候选有成功单线探索，或有已返回先前请求的完整有界反证；证据写明具体范围。不完整反证且没有最终候选试算时，compare=skipped，保留未完成结果而不是伪装完成。最终一步验证仍为 `one-ply-only`，没有被深层检查偷偷改变语义。

记录格式继续使用 `five-llm/v1`；旧 `gomoku-knowledge/v1` 和没有 candidateReview 的历史手记继续有效。沿用 GameService 的深拷贝、undo/new 清理和 Electron 原子保存，没有第二个状态源。失败/取消且未提交的尝试仍不会持久化为落子手记；完整工具审计不是本轮实现范围。

## 回归评测

```bash
bun test tests/forcing-case.test.ts tests/forcing.test.ts
bun test tests/pi-integration.test.ts tests/service.test.ts tests/knowledge.test.ts
just check
just smoke
```

用例包括：

- 实战 H7 反证、I11 拆掉实际杀法、浅层负结果边界。
- 八种棋盘旋转/镜像的反证；由权威引擎验证强制应手，并穷举所有合法末端防守确认均不能阻止下一手成五。
- 自己立即胜优先、对手反杀优先、跳四、长连和满盘和棋。
- 空盘不伪造证明；零预算、节点/时间预算、取消与非法输入。
- 真正 Pi SDK + 本地 SSE：H7 提交前返回反馈、改选 I11、显式保留风险、同批结果不能假装已读、浅负结果不抹去正反证。
- 候选级分支完整性、其他候选不冒充最终候选、不完整状态与棋谱深拷贝隔离。
- 显式棋钟压力与跳过记录；提交前反馈仍扣时，迟到的审查后提交照常判负。

验证结果：`just check` 通过（TypeScript、95 项测试、4244 个断言、构建）；`just smoke` 通过真实 Electron 的下棋/回看/悔棋、布局、棋钟、赛制、超时与音乐回归。

本机对 H7/I11 各运行 25 次默认检查：H7 找到反证（8 节点），中位约 1.29ms、p95 约 2.89ms；I11 预算内未发现（13 节点），中位约 1.30ms、p95 约 2.55ms。此为该局面本机测量，不是所有局面的延迟保证；较复杂局面仍受预算约束并可能返回 incomplete。

本地 SSE 测试只验证真实 Harness 的工具调度和证据契约，不访问外部模型、不消耗 API 额度，不证明真实模型一定选择更好或整体棋力提升。
