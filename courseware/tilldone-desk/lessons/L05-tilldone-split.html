L05 · 拆分与分工

TillDone 的原生拆分

TillDone 有一个 split 动作，但它自己从不决定怎么拆。这一课看清它提供了什么：拆分的规则、提醒拆分的时机，以及让人参与的按钮。

原文：§4阅读约 20 分钟含 3 个互动演示

学完本课，你能够：

  • 写出 Task 和 Model 的数据形状，说出 split 的四条规则。
  • 说出提醒拆分的三个触发点，以及每个触发点选在那个时刻的理由。
  • 解释 spent 什么时候清零，以及分派 subagent 时它的盲区。
  • 描述细分按钮的完整流程：发什么、何时恢复。

01只给时机和账本

本课核心句TillDone 只提供拆分的时机和账本。怎么拆由模型决定。

“账本”指清单本身和 split 动作。它保证拆分后的清单仍然合法。“时机”指三个提醒点和一个人的入口。它们告诉模型“现在该想想要不要拆”。

TillDone 从不自己生成子任务，桌面端也不。哪几个子任务、每个多大，都由有上下文的模型决定。

02数据形状与 split 规则

先看数据形状（state.ts）：

interface Task  { id: number; text: string; status: "idle" | "inprogress" | "done"; from?: number }
interface Model { list: ListState; nudged: boolean; spent: number }

九个动作：new-list、add、start、done、remove、update、list、clear、split。

split 的规则在 state.ts:344-354。

  1. 参数是 id 加 texts[]。texts 至少 2 个，否则返回 “texts (at least 2) required for split”。
  2. 子任务原位替换原任务。子任务带 from = 原 id，id 从 nextId 起编。
  3. 第一个子任务继承原状态，其余为 idle。所以拆分进行中的任务后，仍然只有一个任务在进行。
  4. 已完成的任务不能拆。
Task #N is already done. Use add for new work instead of splitting it.state.ts:347

还有一条和计数有关。当前任务的 id 变了，spent 就清零（state.ts 的 ok()）。拆分进行中的任务时，第一个子任务是新 id，所以它从 0 开始计数。

补充：为什么是“原位”子任务插在原任务的位置上，不是追加到末尾。清单的顺序因此保持“先做什么、后做什么”的原意。from 字段让你追溯每个子任务来自哪里。

    04三个触发点

    先说结论：TillDone 在三个时刻提醒模型考虑拆分。三处文本都定义在 state.ts。

    ① 工具说明里的原则（每次请求都在）

    Keep each task small enough to finish and verify in one focused change. If a task turns out bigger, split it instead of letting it grow; if you find work outside the current task, add it as a new task.state.ts TOOL.description

    ② 刚认领时：SPLIT_CUE

    SPLIT_CUE（state.ts:113）附在 start 结果的末尾。

    Before you start: if this task holds two or more steps you can verify separately, split it now with `tilldone split`.state.ts:113

    理由写在源码注释里：这是模型对任务大小了解最多、还没花任何成本的时刻。

    ③ 做了很久时：每 15 次

    SPLIT_HINT_EVERY = 15（state.ts:116）。toolCalled（state.ts:430）给当前任务的每个非 tilldone 工具调用记 spent + 1。到 15 的倍数时，生成一条拆分提示：

    💡 TillDone: task #N has taken 15 tool calls so far. If it is bigger than one step, split it with `tilldone split` (id=N) and keep going.state.ts:438

    提示的送达有一个细节。工具调用时，工具还没执行，所以 L2 先把提示暂存进一个 Map，键是 toolCallId。等这次调用的 tool_result 回来，再把提示追加到结果末尾（index.ts）。模型不需要额外的 turn。

    提示在 tool_call 时决定，在 tool_result 时送达。依据原文 §4.3 与 index.ts 重画。

    05动手看：15 次提示与盲区

    同一个任务要做很多步工作。比较三种做法：全部自己做、中途拆分、交给 subagent。看提示在第几次工具调用时出现。

    计数器：同样的工作量，spent 和提示怎样变化
    做法：
    把工作量拖到 40，切换三种做法。“全部自己做”在第 15、30 次各提示一次。“第 20 步后 split”：第一个子任务是新 id，spent 从 0 重新数。“分派一个 subagent”：子 agent 内部做的几十步，spent 只记 1 次，提示永远不出现。
    简化模型：每步工作 = 1 次非 tilldone 工具调用；分派时父 agent 先自己做 2 次 read，再调 1 次 subagent；tilldone 自己的调用不计数。
    盲区原文 §7 第 1 条：子进程不加载 TillDone。一次 subagent 调用在 spent 里只算 1 次。分派出去的大任务看起来很“便宜”，不会触发拆分提示。
    补充：面板上的“工具次数”不是 spent任务面板上每个任务旁的工具调用次数由桌面 D-L3 自己数（src/domain.ts:282 的 tool_execution_start），按任务 id 累计，到 15 次标为“偏重”（toolCallsView，src/domain.ts:470）。spent 只数当前任务，当前任务一换就清零。两者会分叉。例如：start #1 做 10 次 bash，start #2 做 3 次，再 start #1 做 6 次。面板上 #1 是 16 次，已标“偏重”；spent 却是 6，模型一次 15 次提示都没收到。所以面板标红不等于模型收到过拆分提示。这是课程作者对照源码的观察，原文没有讨论。

    06人的入口：细分按钮

    先说结论：牧羊人指出任务，模型决定怎么拆。桌面端自己不拆，也不调 split。

    The shepherd points at a task; the model, which has the context, decides the subtasks.src/domain.ts:416

    任务面板上每个未完成任务都有“细分”按钮。点下后：

    1. 桌面端按界面语言取文案 splitRequest，填入 id 和任务文本。
    2. 如果 Pi 空闲，发 prompt。如果正在运行，发 steer。
    3. 桌面端记一条 desk_split_requested，把 id 放进 pendingSplits。按钮变成“细分中…”。

    按钮在两种情况下恢复。第一，下一次 tilldone 结果里，这个任务已经不在或已经完成。模型 split 了它，或者把它标为 done。第二，这次 settle 结束了。第二种覆盖了“模型决定不拆”。

    流程：点“细分”之后，按钮何时恢复
      先点“细分”，再点一次。桌面端忽略第二次，因为 #2 已在 pendingSplits 里。然后分别试三种结局。结局 C 之后按钮仍是“细分中…”，直到 agent_settled。再取消“Pi 正在运行”重来：命令从 steer 变成 prompt。
      依据 src/domain.ts 的 planIntent 与 reduce 移植；消息文案照搬 appearance.ts。任务是演示用例子。
      补充：一处语言耦合splitRequest 是模型能读到的文本，却跟着界面语言变。白皮书 8.5 节把它列为风险 R6：回归测试时，界面设置会成为模型输入的一个变量。

      07门禁与督促

      账本还需要两只手：门禁保证“先认领再动手”，督促保证“没做完不收工”。

      门禁

      门禁 gate（state.ts:378）只拦 GATED_TOOLS = ["bash", "edit", "write", "subagent"]（state.ts:376）。它依次检查三件事：

      1. 清单为空 → noTasks。
      2. 全部完成 → allDone。
      3. 没有 inprogress 任务 → noneActive。
      版本门禁做法后果
      TUI 原版只放行 tilldone 和只读工具 read / grep / find / ls，其他全拦不认识别的扩展加的工具。2026-11-01 Blackjack 运行里，pstack_todo 在 Poteto 会话开头撞上门禁 5 次
      桌面副本（7437421）只拦会改东西的四个工具规划类工具都能通过

      原文的理由是：门禁是工作纪律，不是安全边界。详见 L06 的反转门禁。

      督促

      督促 agentEnd（state.ts:450）在 run 结束时检查清单。有未完成任务且 nudged 为假时，它返回 tilldone-nudge 消息，并把 nudged 置真。L2 用 sendMessage(nudge, { triggerTurn: true }) 发出。

      Either continue working on them or mark them done with `tilldone done`. Don't stop until it's done!state.ts agentEnd

      input 事件复位闩锁。所以每条用户输入最多督促一次。督促之后模型仍然停下，说明它可能真卡住了，该交还给人。L01 的播放器演示了这个过程。

      桌面端怎样交还给人

      桌面端会判定每条督促的结果，并在停下时提示用户。这些都在 D-L3，只给界面，不进模型上下文（原文 §4.5，提交 b89da3a、4965e82）。

      1. 收到 tilldone-nudge 时，addNudge 记下当时未完成的任务 id。
      2. 这次督促起的 run 结束时（下一次 agent_end），judgeNudges 判定结果：全部完成 → done；完成一部分 → partial；一个也没完成 → stopped；清单被换掉 → replaced。拆出的子任务还开着，原任务也算没完成。
      3. 督促消息卡片用界面语言写出结果，例如“⚠ 提醒之后没接着干，#2 还没干完”。模型看到的英文原话折在“TillDone 发给边牧的原话”里。
      4. 任务面板有一行督促统计，例如“催过 1 次，催完没接着干，等你发话”。
      5. Pi 已停下、还有未完成任务、最新一条用户消息之后已经督促过时，输入框上方出现交还提示。
      边牧停下了：{tasks} 还没干完，也已经提醒过它。你可以回复它接着干，或点任务旁的“细分”把任务拆小。src/appearance.ts handoff

      08自测与速记

      拆分一个进行中的任务 #3 成 3 个子任务后，清单里有几个任务是 inprogress？
      子任务原位替换原任务。第一个子任务继承原状态 inprogress，其余为 idle。#3 不再存在。
      为什么 SPLIT_CUE 附在 start 的结果上？
      源码注释原意：the moment the model knows most about its size and has spent nothing on it。
      一个任务里，模型自己做了 2 次 read，再调 1 次 subagent，子 agent 内部做了 50 次工具调用。spent 是多少？
      子进程不加载 TillDone。父进程只看到 2 次 read 和 1 次 subagent，共 3 次。15 次提示不会出现。
      点了“细分”后，模型决定不拆，只继续做别的。按钮什么时候恢复？
      只要 #2 仍未完成，tilldone 结果不会把它移出 pendingSplits。agent_settled 时整个 pendingSplits 清空。

      速记表

      要点一句话
      定位TillDone 只给时机和账本，怎么拆由模型决定
      split 规则≥ 2 个子任务；原位替换；带 from；第一个继承状态；已完成不能拆
      三个触发点工具说明原则；start 时 SPLIT_CUE；每 15 次非 tilldone 工具调用
      spent当前任务 id 一变就清零；不持久化；看不见 subagent 内部
      细分按钮空闲发 prompt、运行中发 steer；任务已拆分或完成，或 settle 结束时恢复
      门禁与督促只拦 bash / edit / write / subagent；每条用户输入最多督促一次
