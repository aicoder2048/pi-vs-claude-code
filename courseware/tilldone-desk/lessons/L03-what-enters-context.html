L03 · 上下文管理

什么进模型的上下文

模型每次请求只看到上下文里的东西。这一课列出 TillDone 和 PStack 各往上下文里放了什么、什么时候放。还要列出哪些东西只给界面、不给模型。

原文：§3.1、§3.2、§3.4阅读约 15 分钟含 2 个互动演示

学完本课，你能够：

  • 用 L3 原则判断一个字段该不该进上下文。
  • 说出 TillDone 和 PStack 往上下文里放的每一类内容、进入方式和频率。
  • 列出不进上下文的东西，并解释界面通道。
  • 说出提示词的三个时机，并解释错误即提示词。

01L3 原则

先说结论：上下文里每一个字段都要有业务理由。理由来自业务语义，不来自工程便利。

上下文管理是手段，业务语义是内容。四层讨论稿 §3
检验标准每个进入上下文的字段，都要能回答“它帮模型做哪个决策”。答不上来的字段，不进上下文。

TillDone 的业务语义很少：清单、门禁、拆分、督促。但每一条都必须让模型看见，否则规矩不起作用。

选一个场景，看这一次请求里模型实际看到哪些块。高亮的块是这个场景新加的。右栏是同一时刻存在、但模型看不到的东西。

组装器：这一次请求，模型看到什么
模型看到的上下文（按顺序）
    同一时刻存在，但不进上下文
      先在“普通请求”下勾选 Poteto Mode，看 system prompt 那一块怎样变化。再切到“第 15 次工具调用”：右栏的 spent = 15 模型看不到，模型只看到结果末尾那一行提示。简化模型：块的顺序和文字依据原文 §3.1、§3.2 和 state.ts；任务名、命令是演示用例子。英文提示文字照源码原样摘录，长句有截断。

      04不进上下文的东西

      先说结论：只帮扩展或界面做决定的东西，不进上下文。原文 §3.2 列了五类。

      • spent（当前任务已用工具次数）和 nudged（本条输入是否已督促）。它们只在扩展内部做决策。
      • 桌面端全部状态：运行中、待送达队列、弹窗、外观。
      • 每个任务的工具次数、模型请求次数。D-L3 从 RPC 事件里数，只给界面。
      • 子 agent 实时树。src/domain.ts:556 的 parseChild 解析 subagent 的 partial result，只给 L4。
      • API 凭据。Pi 自己解析 auth.json，桌面端不转发。
      本节核心句这就是“界面通道和上下文通道分离”。界面通道直接来自 L3 状态，不经过模型转述，也不占上下文。
      补充：spent 和拆分提示的关系spent 这个字段和它的连续值不进上下文。但它到 15 的倍数时，扩展会生成一行提示，追加到工具结果末尾。提示里带着当时的数字（“has taken 15 tool calls so far”），所以模型只在 15、30、45… 这几个点上看到一个数，看不到 16、17、29。也就是说，模型看到的是按 15 采样的“结论”（该考虑拆了），不是连续的“计数器”。这正好符合 L3 原则：模型要做的决策是“拆不拆”，不需要每一次的计数。

      05三个时机与错误即提示词

      先说结论：TillDone 在三个时机把规矩送进上下文。它从不改 system prompt。

      时机文本目的
      事前（每次请求都在）工具说明告诉模型规矩和建议
      事中（触发规矩时）门禁理由、SPLIT_CUE、15 次提示、确认被拒在决策点给出可执行的下一步
      事后（run 结束时）督促消息，列出未完成任务防止半途收工

      “事中”里最省事的一招叫错误即提示词。门禁不在 system prompt 里写“请先建清单”。它等模型真的越过规矩，再用工具错误告诉它下一步该调什么。

      🚫 No TillDone tasks defined. You MUST use `tilldone new-list` or `tilldone add` to define your tasks before changing anything (bash, edit, write, subagent); every other tool stays available for planning. Plan your work first!GATE_REASON.noTasks · §3.4

      门禁按顺序检查三件事。任一不满足就拦下，返回对应的理由：

      1. 清单为空 → noTasks。
      2. 全部完成 → allDone。
      3. 没有进行中的任务 → noneActive。

      桌面副本只拦四个工具：bash、edit、write、subagent（state.ts:376 的 GATED_TOOLS）。其他工具都放行，例如 read 和 pstack_todo。

      06动手看：替模型过门禁

      你来当模型。目标是成功执行一次 edit。每一步选一个工具调用，门禁按 state.ts 的规则判定。门禁拦下调用时，你会看到原样的拒绝理由。照着理由做，就能通过。

      走查：照着错误提示，几步能做成第一次 edit
        先直接点 edit，读拒绝理由，再照着做。最少 3 步：tilldone add → tilldone start → edit。
        然后勾上“TUI 原版门禁”，点 pstack_todo set，门禁会拦下它。原文说，2026-11-01 Blackjack 运行里，原版门禁这样拦了它 5 次。简化模型：判定逻辑照 state.ts 的 gate；任务名是演示用例子；没有模拟计费门和确认弹窗。TUI 原版放行表依据原文 §4.4。

        07自测与速记

        TillDone 用哪种方式把规矩送进上下文？
        原文 §3.1、§3.4：TillDone 从不改 system prompt。事前靠工具说明，事中靠工具结果和工具错误，事后靠自定义督促消息。
        下面哪一项不进模型的上下文？
        原文 §3.2：spent 和 nudged 只在扩展内部做决策。模型只在满 15 的倍数时看到一行提示，提示里带着那一刻的数字；连续的计数不进上下文。
        清单为空时，模型直接调用 edit，会收到什么？
        这就是错误即提示词：在越过规矩的那一刻，用工具错误给出可执行的下一步。
        PStack 的 poteto-mode/SKILL.md 全文怎样进入上下文？
        原文 §3.1：整份 SKILL.md 只展开一次。每次请求追加到 system prompt 的是另一段短说明。
