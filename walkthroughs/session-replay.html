session-replay.ts

注册一个 /replay 命令，把当前分支上的 user / assistant / toolResult 消息列成时间线，在居中的浮层里用 ↑↓ 浏览、回车展开。216 行，订阅 session_start（只设主题），真正的入口是 pi.registerCommand。这是走读里第一个命令：它挂在用户输入上，却完全不进双循环。

    ② 提示词上下文

    session-replay 不在安装、控制、装配任何一段：不写提示词，/replay 这几个字也不会进上下文（命令在 input 之前就返回了，不会变成 user 消息）。它读的是会话树：和 LLM 看到的消息来自同一批落盘条目，但取法不同，所以浮层里的时间线和模型的上下文并不一一对应。

    下面的模拟器用 JS 复刻了 SessionReplayUI 的选中、展开和滚动逻辑，并按 Pi 合成浮层的方式（居中、没有 maxHeight）放进一个固定高度的终端里。调大会话条数，用 ↑ 往上翻，看浮层怎么长高、选中项怎么跑出屏幕。

    Bug：往上翻会让浮层越来越高，超过终端后选中项被裁掉。第 80 行 items.slice(this.scrollOffset) 只有起点没有终点：从 scrollOffset 一直画到最后一条。刚打开时 scrollOffset 是“最后 6 条”的起点，看着正常；按 ↑ 翻过顶部后，scrollOffset 跟着减小，浮层多画一条；翻到第 0 条时所有条目都画出来。浮层没设 maxHeight（第 208 行），Pi 按居中公式放置（tui.ts:1354），高度超过终端时上下两头都在屏幕外（推断），而选中项恰好在顶部，于是看不见了。另外第 202 行把 height 写死成 30，和终端实际高度无关。修法：render 里用真实行数（如 tui.terminal.rows）算 pageSize，第 80 行改成 slice(scrollOffset, scrollOffset + pageSize)。模拟器里调大条数、连按 ↑ 即可复现。
    “+间隔”标在了下一条上。第 159 行用相邻两条消息的 timestamp 相减。但 assistant 消息的 timestamp 是请求开始的时间（ai/src/types.ts:601），模型花的时间要等到下一条 toolResult 才体现出来：assistant 那条几乎总是 “+0s”，模型思考了 40 秒，显示在后面的 Tool 条目上。想看模型耗时，应读 assistant 的 durationMs（:608）。另外第 160 行在 if (!text) continue 之前就更新了 prevTime，被跳过的条目也会“吃掉”一段间隔。
    浮层是快照。条目在命令执行时一次读完（第 148 行），之后 render 只画这份数组。场景 B 里 agent 在浮层打开期间继续跑，新落盘的消息不会出现；正在流式输出的那条在执行命令时还没落盘（落盘发生在 message_end 之后，agent-session.ts:1165），也不在里面。要看最新的，关掉再 /replay 一次。
    命令不经过 input，也就绕过了所有 input 订阅者。扩展命令在 prompt() 第一步就被执行（agent-session.ts:2101），早于 _runInputHandlers（:2117）。和第 11 篇 purpose-gate 这类改写输入的扩展一起装时，/replay 不会被它们看到。这是 Pi 的设计：命令自己管理和 LLM 的交互（源码注释写的是 “via pi.sendMessage()”）。
    小处。第 5 行 import 的 truncateToWidth、pi-tui 的 getMarkdownTheme，以及第 199 行的 kb 参数都没用到。第 107–108 行的预览不论长短都在末尾加 “...”。第 113 行只有可见条目少于 15 条时才在条目之间加空行，所以条目多的时候排版会突然变紧。

    小结

    session-replay 是走读里第一个命令：pi.registerCommand 只登记，用户输入 /replay 时 prompt() 在第一步就把它截走执行，不发 input、不起 run，双循环从头到尾没转过。它读的是会话树而不是装配后的上下文，所以能看到被压缩掉的原文，却看不到 custom 消息。下一篇 cross-agent.ts 也注册命令，但命令最后会发出一条用户消息，第一次让命令发起一次 settle。
