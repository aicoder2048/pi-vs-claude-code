    ② 提示词上下文

    damage-control 站在控制这一段：它不改系统提示词，不改用户输入，但它决定 assistant 发出的一个 toolCall 最后变成什么样的 toolResult，而 toolResult 会被装配进下一次请求。它的设计意图是把 reason 写进 toolResult，让模型读到 “DO NOT attempt to work around…”。实际上 ctx.abort() 抢先一步，进上下文的只是 Operation aborted。

    入口段本扩展改了什么LLM 看得到吗
    系统提示词 / 工具列表安装不改：bash、read 等工具照常提供给模型–
    input / before_agent_start / context控制不订阅–
    tool_call 返回值控制放行，或者 block + reason。reason 本该成为 toolResult 的正文（agent-loop.ts:756）当前代码下看不到 reason，只看到 Operation aborted
    pi.appendEntry旁路往会话里写 damage-control-log 条目（tool、input、rule、action）不会：session-manager.ts:125 写明 CustomEntry 不参与 LLM 上下文
    ctx.ui.notify / setStatus / confirm旁路（L4）提示用户、问用户不会

    Bug：ctx.abort() 让精心写的 reason 永远到不了模型。第 215、225 行先调 ctx.abort()，再 return { block: true, reason }。在 TUI 里 ctx.abort() 经 abortHandler → restoreQueuedMessagesToEditor → session.abort()，而 session.abort() 在第一个 await 之前就同步调了 agent.abort()（agent-session.ts:2506 → agent.ts:351）。handler 一返回，prepareToolCall 先检查 signal?.aborted（agent-loop.ts:748），直接产出 "Operation aborted"，走不到读 reason 的第 755 行。结果是：“DO NOT attempt to work around this restriction…”这段话从来不会出现在 toolResult 里。并行执行时，同一批里先准备好、还没开跑的工具也会变成 Operation aborted（agent-loop.ts:630），后面还没准备的直接跳过（:623）。
    修法：删掉两处 ctx.abort()，返回 { block: true, reason, terminate: true }。terminate 正是 Pi 为这种情况准备的字段（types.ts:1462）：工具结果照常写进上下文，这一批结束后 run 不再请求模型（agent-loop.ts:281）。注意 terminate 要求这一批每个结果都带它才会提前结束（agent-loop.ts:700），批里有被放行的工具时，模型还会再被请求一次，并读到 reason。场景 A 和场景 C 对比了两种写法。
    Bug：setStatus 少传了 key，状态行从不显示。接口是 setStatus(key, text)（types.ts:166），第 103、213、223 行只传了一个字符串，于是 key 是那段文字、text 是 undefined，footer-data-provider.ts:147 把它当成“清除这个 key”。加载时不报错（推断：jiti 只转译、不做类型检查）。修法：ctx.ui.setStatus("damage-control", `…`)。
    Bug：bash 的只读检查几乎拦下所有提到只读路径的命令。第 174 行注释说这是“可能修改”的启发式，但条件里的 /[\s>|]/.test(command) 只要命令里有一个空格就成立。于是 cat package-lock.json、ls build/、/usr/bin/env python3 x.py（命中 /usr/、/bin/）都会被当成“may modify read-only path”拦下。模拟器里点对应的预设就能看到。修法：只在出现重定向、sed -i、rm、mv、tee 等写操作时才判定，例如 /(>|\bsed\s+-i\b|\brm\b|\bmv\b|\btee\b)/。
    Bug：bash 的敏感路径检查不认通配符。第 163 行用 command.includes(zap)，而 zeroAccessPaths 里有一半是 *.pem、*.env、*-credentials.json 这样的通配模式，字面上永远不会出现在命令里。结果 read server.pem 被拦（read 走第 55 行的 isPathMatch，认通配），bash cat server.pem 却放行。修法：把命令按空白切成 token，对每个 token 调 isPathMatch。
    路径匹配偏宽。isPathMatch 最后还有一个子串兜底（第 76 行 includes(resolvedPattern)）：.env 会命中 src/load.env.ts；目录规则 dist/ 经 path.resolve 去掉末尾斜杠后，用 startsWith 也会命中 distribution.ts。方向是“宁可错拦”，对安全扩展说得通，但会打断正常工作。
    启发式的边界。bash 检查是字符串匹配：cat $HOME/.ssh/id_rsa、cat ~/".ssh"/id_rsa、先 cd ~/.ssh 再 cat id_rsa 都能绕过。另外第 125–129 行只认 read / write / edit / grep / find / ls / bash，Pi 的 powershell 工具（types.ts:1389）不在检查范围内。这类扩展防的是模型“手滑”，挡不住刻意绕过。
    失败时的方向：都是拦。确认框 30 秒没人理，showExtensionSelector 得到 undefined，confirm 返回 false（interactive-mode.ts:2764），按拒绝处理，但日志里写的是 blocked_by_user，分不出是用户拒绝还是超时。YAML 里有一条非法正则时，第 152 行的 new RegExp 抛异常；emitToolCall 不接异常（runner.ts:1255），prepareToolCall 的 catch 把它变成一条错误结果（agent-loop.ts:783），于是每一条 bash 都被拦下，错误信息是正则语法错误。
    和 just 里的另外两个扩展叠加。just ext-damage-control 同时装 minimal 和 theme-cycler。minimal 用 setFooter 换掉了内置页脚，而扩展状态只由内置页脚画（footer.ts:290），所以即使修好 setStatus，这个组合下状态行也看不到，theme-cycler 的状态也一样。这不是 damage-control 写错，是页脚槽的取舍（第 02 篇）。另外多个扩展都订阅 tool_call 时，按加载顺序问，第一个返回 block 的生效，后面的不再被调用（runner.ts:1259）。

    小结

    damage-control 把一个回调的返回值变成了 run 内循环的分叉：tool_call 返回 block，Pi 就跳过执行、把 reason 作为错误结果写进上下文。它多做的一步 ctx.abort() 从 L3 反过来打断 L1，但 prepareToolCall 先看 abort 再看 block，于是 reason 被丢掉了。下一篇 damage-control-continue.ts 用同一套规则，去掉了 abort，改为把可操作的反馈写进 toolResult，让 agent 换条路继续干活。
