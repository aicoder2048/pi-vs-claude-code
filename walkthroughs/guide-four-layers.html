四层架构：设计自定义 Pi Harness

每篇走读都把扩展拆成 L1 Runtime、L2 扩展、L3 业务、L4 UI 四层。这篇指南横着看四层：每一层能不能动、靠什么动、放什么代码；以及为什么做一个领域专用的 Pi Agent Harness 时，L3 最难。具体案例链接到系列各篇，四层落成文件的完整例子见 12-b tilldone 四层版。

四层一览

点一层，看它能不能改、靠什么改、在 tilldone 四层版里对应哪个文件。

L1：继承 Pi，不改它

自定义 harness 不 fork Pi。双循环、会话树、compaction、工具执行顺序都按 Pi 的来；我们能改的是 Pi 留出来的口子。下表左边是“动不了”的部分，右边是 Pi 在这一块留下的替换口。

Pi 提供的不 fork 就动不了的Pi 留的替换口
双循环（settle 转 run，run 转 turn）循环的形状、判断顺序（见 一个 turn 的内部）只能在 L2 的插点上影响它，例如 turn_end 要求续跑、agent_end 排消息
会话树与投影存储格式、投影规则扩展往里写：工具结果的 details、pi.appendEntry（types.ts:1747）
模型调用请求流程models.json、自定义 provider（pi.registerProvider，types.ts:1859）、虚拟模型路由
系统提示词默认提示词的拼装方式SYSTEM.md 整个替换、APPEND_SYSTEM.md 追加、before_agent_start 按次替换
内置工具工具的执行机制setActiveTools（types.ts:1778）、--tools、SDK 的 tools / noTools / customTools
运行宿主–交互式 TUI、print、JSON 事件流、RPC、SDK（createAgentSession）
对照：不是所有 harness 都把 L1 当成“动不了”。DeepSeek Harness 建在 Cordis 插件内核上，模型适配、工具、会话、沙箱、存储、调度，连 agent loop 本身和 UI 都是插件，可以在配置里替换（DataCamp 介绍、DeepInfra 评测）。Pi 的取舍相反：循环固定，开放的是循环上的插点。两种做法的利弊放在 discussions/2026-10-28-l4-web-desktop-and-plugin-harness.md，那是设计讨论，不是这套走读的前提。

L2 的 how：作用域、共享与调用 L3

扩展是一个 export default function (pi)。理解它的作用域，就知道状态放哪、回调之间怎么共享、L2 怎么调 L3。

export default function (pi: ExtensionAPI) {          // ① 每个 runtime 调一次工厂（loader.ts:627）
  let model = INITIAL_MODEL;                            // ② 闭包变量：下面所有回调共享这一个格子

  pi.on("tool_call", (e) => gate(model, e.toolName));   // ③ 读：把“当前状态 + 事件”交给 L3 纯函数

  pi.registerTool({ name: "tilldone", /* … */
    async execute(_id, params, _s, _u, ctx) {
      const r = runTool(model, params);                 // ④ L3 返回新值，L2 只负责换格子
      if (r.next) model = r.next;
      paint(ctx.ui, model.list);                        // ⑤ ctx 每次事件都新给一份，用完即弃，不要存
      return { content: [{ type: "text", text: r.text }], details: r.details };  // ⑥ details 进会话树
    },
  });

  pi.on("session_start", (_e, ctx) => { model = restore(model, detailsOnBranch(ctx)); });  // ⑦ 从会话恢复
}
问题答案依据
同一个扩展的不同回调怎么共享变量？工厂函数里的闭包变量（②）。所有 pi.on、工具、命令都在同一次工厂调用里注册，读写同一个变量loader.ts:627 调工厂
闭包能活多久？一个 runtime。/reload、新会话会换新 runtime、重新调工厂，旧闭包作废；旧 runtime 上的调用会抛 stale 错误loader.ts:167
那状态怎么跨 reload、跨分支？写进会话树（工具结果的 details 或 pi.appendEntry），在 session_start / session_tree 里恢复（⑥⑦）tilldone 两版都这么做
L2 怎么调 L3？直接 import L3 的纯函数，传入“当前状态 + 输入”，拿回“新状态 + 要做的事”（③④）。L3 不 import Pi，也不 import L412-b 的结构测试强制这一点
ctx 是什么？每次事件 Pi 新给的一份上下文：ui、sessionManager、model… 只在这次回调里用⑤
不同扩展之间怎么共享？pi.events 事件总线（types.ts:1917），或者各自读会话树。不要互相 import 对方的闭包–

扩展以外的插点

扩展不是唯一的插入方式。Pi 文档的建议是先用能力最弱、刚好够用的机制（quickstart 的 “Choose how to customize Pi”）。下表按“改什么”排，越往上越轻。

机制放在哪改什么近似对应的层

SYSTEM.md / APPEND_SYSTEM.md~/.pi/agent/ 或 .pi/整个替换 / 追加系统提示词L3 的“文字”部分

settings.json、keybindings.json、主题agent 目录或 .pi/默认模型、工具、资源路径、按键、配色L1 的配置面 / L4
MCP、models.json、自定义 provideragent 目录或 .pi/，provider 由扩展注册外部工具、模型接入L1 的替换口
扩展extensions/ 或 -e回调、工具、命令、UI：上一节的全部插点L2（+ 它调用的 L3、L4）

L3：为什么最难

L3 不只是“写业务代码”。它要同时满足三股力量，而且每一股都会把一部分逻辑推向 L2 或 L4。这也是讨论记录里那句话：上下文管理是手段，业务语义是内容。点一股力量，看它拆出哪些问题、各落在哪层、系列里哪几篇是案例。

L4：Pi TUI 能画什么

L4 是独立于上下文的数据通道：画在屏幕上的东西模型看不到，也不经过模型转述。Pi 的 L4 是终端界面，下表是扩展能用的组件，以及它们在 RPC 模式（由别的程序驱动 Pi）下还剩什么。

组件显示在哪RPC 模式案例
setStatus页脚状态区转成协议消息，客户端自行显示12
setWidget编辑器上方或下方转成协议消息03、16
notify、setTitle通知、终端标题转成协议消息09
confirm / select / input / editor对话框请求 / 应答子协议，客户端回答12、10
setFooter / setHeader替换页脚 / 页头不生效01、02
custom（浮层 / 占位组件）任意 TUI 组件不生效（返回 undefined）07
renderCall / renderResult聊天区的工具行由客户端自己渲染事件12

RPC 一列来自 Pi 1.4.0 文档 rpc-extension-ui.md。这意味着：如果将来要做 Web 或桌面界面，依赖 setFooter、custom 的 L4 代码都得重写一份；而 L3 的选择器（例如 tilldone 的 countByStatus、current）可以原样复用。图片、three.js 动画、富表格这类视觉内容超出终端能力，可能的方向（扩展内起本地 web 服务、RPC/SDK 宿主 + Web 客户端、Electron 桌面壳）和取舍记在 discussions/2026-10-28-l4-web-desktop-and-plugin-harness.md。
