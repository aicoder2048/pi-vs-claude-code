subagent-widget.ts

在后台跑子代理：/sub 任务 或模型调用 subagent_create 起一个 pi 子进程，编辑器上方为每个子代理挂一个实时 widget；子代理跑完后，结果用 pi.sendMessage(…, { deliverAs: "followUp", triggerTurn: true }) 送回主会话。593 行，订阅 session_start，注册 4 个工具、4 个命令。第 13–15 篇的子进程都卡在主 agent 的工具阶段里；这一篇不等：工具立即返回，子进程在循环之外跑，结束时再把主 agent 叫起来。
运行：just ext-subagent-widget（同时加载 pure-focus 和 theme-cycler）

    ① 四层结构

    第 1–4 步是启动链。第 5–9 步是派出子代理：工具起进程后马上返回，主 agent 的循环继续往下走。第 10–15 步是子代理结束后：L3 的 close 回调经 L2 的 sendMessage 回到 L1，按主 agent 的状态并入当前 run 或起新的 settle。

    ② 提示词上下文

    主 agent 的上下文里，子代理出现两次。第一次是工具结果，只有一句“Subagent #1 spawned … running in background”。第二次是子代理结束后送来的 custom 消息：任务、耗时和最多 8000 字的结果，display: true 所以聊天区也看得到。它和用户消息一样落盘、进上下文，并且会让模型再回应一次。子代理自己的上下文在另一个进程里，存在 ~/.pi/agent/sessions/subagents/ 下的会话文件中，/subcont 会接着这个文件继续。

    Bug：/reload、/new 之后，旧的子代理成了孤儿，结束时回传会抛错。第 581–592 行的 session_start 想 kill 正在跑的子代理，但 /reload 和换会话都会重新执行扩展工厂（第 115 行），新闭包里的 agents 是空的，这段循环永远什么都杀不到。旧实例里的子进程继续跑；Pi 在 /reload 时已经把旧的扩展运行时标记为失效（agent-session.ts:3724），子进程结束时旧闭包里的 pi.sendMessage 会在 assertActive 处抛出 “This extension ctx is stale…”（loader.ts:385、:168）。这个异常发生在子进程的 close 事件回调里，没有人接（推断：会变成进程级的未捕获异常；没有实际触发验证）。结果没有送达，旧 widget 也可能残留。修法：订阅 session_shutdown（它在 invalidate 之前发出，agent-session.ts:3723），在那里 kill 所有子进程、清掉定时器。场景 C 演示了这个时序。
    结果回来时会让主 agent 再说一次话。triggerTurn: true 的意思是：主 agent 空闲时，一条子代理结果就会起一次完整的 settle（第 12 篇讲过的外循环入口之一）。同时派出 3 个子代理，就可能先后起 3 次 settle（后到的如果撞上前一个还在跑，会变成 follow-up 并入）。用户此时如果正在编辑器里打字，聊天区会被这些回合插进来。这是“后台跑”的代价，也是本扩展有意的设计。
    结果文字里混着 stderr。第 262–267 行把子进程 stderr 的输出也推进 textChunks，和 stdout 的 text_delta 混在一起，最后一起作为 “Result” 送回主 agent。子进程打印的警告、Node 的弃用提示都会进主上下文。另外和第 14 篇一样，多个 turn 的文字首尾相接、没有分隔。
    会话文件只增不删。每次 /sub 或 subagent_create 都在 ~/.pi/agent/sessions/subagents/ 下新建一个 subagent-N-时间戳.jsonl（第 122–126 行），/subrm、/subclear、session_start 都不删文件。和第 13 篇不同，这些文件在家目录下，跨项目累积。
    widget 刷新很频繁。子进程每吐一个 text_delta，updateWidgets 就把所有子代理的 widget 各重装一遍（第 133–186 行，每个 setWidget 都会先移除再创建组件），外加每个运行中的子代理每秒一次。并发三四个子代理时，这是 TUI 上最忙的地方。只更新数据、调 requestRender 就够了。just ext-subagent-widget 同时装的 pure-focus 把页脚清空，正好给这些 widget 腾出空间。

    小结

    subagent-widget 和第 13–15 篇用同样的子进程，挂法却不同：工具只负责起进程、立即返回，子代理在循环外运行，结束时用 sendMessage + triggerTurn 回到主会话，主 agent 在跑就并入当前 run，空闲就起一次新的 settle。这让主 agent 不被卡住，但也意味着子进程的生命周期要自己管：会话被替换时，没有 session_shutdown 清理，旧子代理就成了孤儿。下一篇 coms.ts 把这种“从循环外把消息送进来”的手法推广到跨会话通信。
