purpose-gate.ts

会话一开始就弹框问“这个 agent 的目的是什么”，答了才放行：目的显示在编辑器上方的 widget 里，并追加到每次请求的系统提示词末尾；没答之前，任何提问都被 input 拦下。84 行，订阅 session_start、before_agent_start、input 三个事件。这一篇第一次订阅 input：settle 外循环最前面的那道门。
运行：just ext-purpose-gate（同时加载 minimal）

    ① 四层结构

    第 1–7 步是启动链：session_start 发起问询后立刻返回，弹框从此占住编辑器的位置，直到答完才换成 widget。第 8–13 步是答完之后的一次提问：先过 input 这道门，再在 before_agent_start 里把目的追加到系统提示词。

    ② 提示词上下文

    purpose-gate 同时站在控制的两头：input 决定用户消息能不能进来，before_agent_start 决定系统提示词长什么样。和第 10 篇一样，系统提示词的改动走的是“强制提示词”那条路：本次 settle 有效，只在请求里投影，不记进会话。不同的是本扩展把内容追加在末尾，system-select 是加在前面。

    东西段本次 settle记进会话吗/reload、/new、/resume 之后
    被 handled 的消息控制不开始不记：prompt() 在落盘之前就返回–
    <purpose> 段控制所有 run、turn 都带不记（同第 10 篇的强制提示词）闭包清空，重新弹框
    purpose widget– （UI）–不记工厂重跑后重新问，答完才重新挂

    ③ 业务穿透

    模拟器分两半。左边复刻 input 这道门：选消息从哪来、目的填没填、弹框是不是正占着编辑器。右边复刻 before_agent_start 的接力：和第 10 篇的 system-select 一起装时，按 -e 顺序拼出最终的系统提示词。

    Bug：没有 UI 的模式下，问询循环永远停不下来。第 38 行的 while (!purpose) 只有用户答了才会退出。没有 UI 时（print 模式、没接 UI 的 SDK），ctx.ui 是一个空实现，input 固定返回 undefined（runner.ts:334）。于是循环永远拿不到答案；而且每一轮 await 的都是已经 resolve 的 Promise，只让出微任务，不让出事件循环（推断：会把进程卡在 100% CPU，没有实际在 print 模式下跑过）。void 让 session_start 本身不卡，但后面的一切都等不到执行。修法：第 67 行前加 if (!ctx.hasUI) return;（applyExtensionDefaults 自己就是这样判断的），无 UI 时干脆不关门，或者在 input 里对 source === "rpc" 放行。
    弹框关不掉。输入框里 Esc 和 Ctrl+C 都算“取消”（tui.select.cancel，extension-input.ts:84），取消得到 undefined，第 47 行提示 “Purpose is required.” 后立刻再弹一次。这是“必须先声明目的”的设计，但用户想先看看会话、或者只想用 /replay 这类命令都不行，只能先随便填一句。
    input 这道门，在 TUI 里用户其实碰不到。对话框是压进编辑器位置的（showTopExtensionDialog 把编辑器换下去），没答之前用户根本没有地方输入提问。第 77–83 行真正拦住的是程序发出的消息：别的扩展的 sendUserMessage（第 08 篇 cross-agent 的命令就是这样）、RPC / SDK 客户端的 prompt。另外，扩展命令在 input 之前就被执行了（第 07 篇），这道门拦不住任何命令。场景 B 演示的是被拦住的那种情况。
    目的只活在内存里。purpose 是闭包变量，<purpose> 段又走“强制提示词”那条不落盘的路，所以 /reload、/new、/resume 之后都要重新填，会话文件里也看不出当时的目的是什么。想保留，可以答完后 pi.appendEntry("purpose", { text })，session_start 时从 ctx.sessionManager 读回来，读到就不再弹框。
    和其他扩展叠加。和第 10 篇的 system-select 一起装时，两个 before_agent_start 按 -e 顺序接力，一个加前面、一个加后面，谁先谁后结果都一样：agent 正文 + 默认提示词 + <purpose>。模拟器右半边可以验证。widget 方面，第 03 篇讲过：purpose 要等用户答完才 setWidget，所以总排在同在 aboveEditor 的其他 widget 下面。另外 widget 用的是写死的 synthwave 颜色，而本扩展自己的主题是 tokyo-night，两者对不上。

    小结

    purpose-gate 守在 settle 外循环的最前面：input 返回 handled，prompt() 直接结束，settle 根本不开始；放行之后，before_agent_start 再把目的追加到系统提示词末尾。它让人看到 input 和 before_agent_start 的分工：前者决定消息进不进来，后者决定模型带着什么指令去处理它。下一篇 tilldone.ts 是回调最多的一篇：input、tool_call、agent_end 续跑和会话分支都会用到。
