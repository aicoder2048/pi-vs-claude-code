怎么读“双循环与回调点”

18 篇走读的“双循环与回调点”这张图看起来几乎一模一样。这是故意的：图里画的是 Pi，不是扩展。这篇讲清楚哪些部分每篇都一样、哪些不一样，以及读图时容易看错的地方。

为什么每篇的图都一样

图里的两个框是 Pi 自己的运行流程：

  • settle 外循环 · 续跑—停稳（重复 run）agent-session.ts:1873 _startRun：用户一次回车，可能起好几个 run，直到没有续跑的理由才停稳。
  • run 内循环 · 模型—工具（重复 turn）agent-loop.ts:188 runLoop：每个 turn 请求一次模型，有工具调用就执行工具，再进下一个 turn。

扩展改不了这两个循环的形状，只能在沿途发出的事件上挂回调。所以节点和箭头对任何扩展都一样，每篇只是在上面标出“我挂在哪”。这张图由共用脚本 WT.loops() 统一生成，每篇只声明三样东西：

① 橙框（hit）

本扩展用到的节点。每篇真正不同的地方主要在这里。

② 格子里的小字（sub）

默认写节点的通用含义；扩展用到的格子会改写成“扩展在这里做什么”。

③ 图例（legend）

图下方的说明：橙框各是什么，以及不在图里的回调，比如 render()。

    四步读法

    1. 先看橙框落在哪。橙框在外循环入口（input、before_agent_start），说明扩展管的是“这次提问怎么开始”；在内循环的工具格，说明它管每一次工具调用；在 agent_end，说明它会影响“要不要再跑一个 run”。
    2. 再看橙框里的小字。同样是工具格，damage-control 写的是 “tool_call（执行前，可 block）”，tool-counter 写的是 “tool_execution_end”。一个在工具执行前拦，一个在执行后计数，时机完全不同。
    3. 然后看图例。页脚、widget 的 render()，以及快捷键，都不走双循环，图里画不出来，只会写在图例里。只挂 session_start 的扩展（minimal、pure-focus），主要工作其实都在图例里提到的 render() 中。
    4. 最后播放场景，盯住 run / turn 计数。计数器里 run 变成 2，说明外循环转了第二圈，这是扩展能不能“催续跑”的直接证据。tilldone 那篇第一次出现这种情况。

    #扩展橙框实际订阅读图要点

    18 篇里从没亮过的节点：agent_start、turn_start / turn_end、context → LLM、message_*、agent_before_settle、agent_settled。这些插口 Pi 都提供了，只是这批扩展没用到。

    容易看错的地方

    橙色的 input 格不一定表示订阅了 input 事件。session-replay、theme-cycler、system-select、cross-agent、subagent-widget 都没有 pi.on("input")，它们注册的是斜杠命令。命令在 prompt() 入口、input 事件之前就被截走并执行（agent-session.ts:2101），不起 run。图上没有单独的“命令”节点，所以借用了离它最近的 input 格，并把小字改成 “prompt() 截走 /xxx”。真正订阅 input 事件的只有 purpose-gate 和 tilldone。读的时候看小字，别只看颜色。
    session 格代表一组事件。theme-cycler、coms、coms-net 还订阅了 session_shutdown，tilldone 还订阅了 session_tree、session_fork、session_switch。图上只有一个 session_start 格，这些事件都算在它头上，具体是哪个要看小字或图例。
    工具格也包含扩展自己注册的工具。agent-team、agent-chain、pi-pi 没有订阅任何 tool_* 事件，工具格亮是因为它们用 registerTool 注册的工具在这一格里执行。这些工具会再起子 pi 进程，每个子进程又有自己完整的一套双循环，这一层嵌套图上画不出来。
    快捷键和循环外的消息也不在图里。theme-cycler 的快捷键在编辑器里就被拦下（custom-editor.ts:90），根本不经过 prompt()。subagent-widget、coms、coms-net 在循环外（子进程退出、socket 或 SSE 回调里）调 sendMessage 唤醒 agent，入口同样不在图上。
