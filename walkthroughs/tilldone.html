tilldone.ts

给 agent 套上任务纪律：先用 tilldone 工具列出任务、把一项切到“进行中”，其他工具才放行；run 结束时还有没做完的任务，就自动催一次，让 agent 接着干。726 行，订阅 session_start、session_tree、tool_call、agent_end、input 等 7 个事件，注册 1 个工具、1 个命令。这一篇第一次注册工具，也第一次从 agent_end 让 settle 外循环再转一圈。
运行：just ext-tilldone（同时加载 theme-cycler）

    ② 提示词上下文

    tilldone 不改系统提示词，却从三个方向往上下文里放东西。安装：注册的工具带着一段描述（“You MUST add tasks before using any other tools…”），Pi 把它写进系统提示词的工具段和工具声明。控制：tool_call 的 block reason 成为 toolResult（没有 abort，同第 06 篇）；agent_end 注入一条 custom 消息。状态：任务清单不存文件，而是存在每次 tilldone 工具结果的 details 里，跟着会话树走。

    ③ 业务穿透

    模拟器原样复刻了扩展的状态逻辑（第 160–323 行和工具的 add / toggle / remove / clear 分支），包括 makeDetails 只浅拷贝数组这一点。左边点工具动作，每次都会像真实会话一样“落盘”一条带 details 的结果；右边用 tool_call 门测试别的工具，或者 “/tree” 回到某一条结果，对比内存里重建的状态和磁盘上那一刻写下的状态。

    近似之处：clear / new-list 的确认框一律当作“同意”；/tree 只模拟“回到某条结果之后”，不模拟分支摘要；磁盘快照用 JSON.stringify 在“落盘”那一刻取，对应 session-manager.ts:1187 的追加写入。

    Bug：details 和内存里的任务共用同一批对象，/tree 回去看到的是“现在”的状态。makeDetails（第 168–175 行）只是 [...tasks] 浅拷贝，数组里的 Task 对象和内存里的是同一批。Pi 落盘时会把当时的 JSON 写进文件（session-manager.ts:1187），但内存里的会话条目保存的是对象引用，没有拷贝（appendMessage）。之后 toggle（第 500 行）、update（第 573 行）原地改对象，早先那些结果里的 details 也跟着变了；reconstructState 又直接 tasks = details.tasks（第 315 行），之后 add 的 push 会塞进那条旧结果的数组。结果：同一个进程里 /tree 回到 “#1 刚加上” 那一刻，显示的却是 #1 已完成；退出后 /resume 从文件读，才是对的。修法：makeDetails 里 tasks: tasks.map(t => ({ ...t }))，reconstructState 里同样拷一份。模拟器里先 add、toggle 两次，再 /tree 回第 2 条就能看到两边不一致。
    Bug：setStatus 两个参数写反了。第 289、293 行是 setStatus(文字, "tilldone")，而签名是 setStatus(key, text)（types.ts:166）。于是每次文字不同（任务数变了），就以那段文字为 key 新增一条状态，值都是 “tilldone”，旧的从不删除（footer-data-provider.ts:146）。因为本扩展自己换掉了页脚，这些状态平时看不到；但如果别的扩展把页脚换回内置的，状态区会出现一串 “tilldone tilldone tilldone”。修法：setStatus("tilldone", 文字)。
    同一条回复里“先 toggle 再干活”会被拦。默认并行执行时，executeToolCallsParallel 先把这一批的每个调用依次 prepare（agent-loop.ts:614，tool_call 就在这里触发），全部 prepare 完才一起执行（:656）。模型在一条回复里发 tilldone toggle #1 + read a.ts，read 的门检查发生在 toggle 真正执行之前，看到的还是“没有进行中的任务”，被拦。模型下一个 turn 重试就过了，只是多花一个 turn。场景 B 演示了这个时序。若把 tilldone 工具设为 executionMode: "sequential"，整批会改为逐个 prepare + 执行（agent-loop.ts:526），就不会这样。
    催办的节流靠 input。nudgedThisCycle 只在用户发消息时（第 385–388 行）清零，所以一次提问最多催一次：第二个 run 结束时即使还没做完，也不会再催，外循环停稳。这避免了无限续跑。代价是：催办消息本身走 sendMessage，不经过 input；如果别的扩展用 sendUserMessage 发消息，会经过 input 并清零，可能多催一次。另外 agent_end 不区分用户按 Esc 中止的情况：中止后照样会排一条催办（推断：会在下一次提问时随 steer 送达，未实际验证）。
    旧事件名。第 329–330 行订阅的 session_switch、session_fork 在 Pi 1.4.0 里已经没有了：换会话、fork 都改为发 session_start，用 reason 区分（types.ts:758）。因为第 325 行的 session_start 本来就会重建状态，所以功能上没缺，只是这两行是死代码。
    和其他扩展叠加。tilldone 每次 refreshUI 都重新 setFooter（第 297 行），页脚槽是“最后一个赢”（第 02 篇），所以只要 agent 动一下任务，tilldone 就会把别的扩展（minimal、tool-counter）的页脚抢回来，也会挡住 theme-cycler 的状态。tool_call 门和第 05 篇 damage-control 叠加时，谁先 -e 谁先问，任何一个 block 就生效。

    小结

    tilldone 把扩展能挂的位置几乎用了一遍：用 registerTool 给模型一个新工具，用 tool_call 在 run 内循环里设门，用工具结果的 details 把状态存进会话树，用 agent_end + triggerTurn 让 settle 外循环再转一圈，再用 input 给续跑节流。下一篇 agent-team.ts 换到编排：注册的工具会启动子代理，并用 setActiveTools 控制主 agent 能做什么。
