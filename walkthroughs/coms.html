coms.ts

同一台机器上的几个 Pi 会话互相发消息：每个会话在 ~/.pi/coms/sockets/ 下监听一个 unix socket，在 ~/.pi/coms/projects/<项目>/agents/ 下登记自己；模型用 coms_send 给同伴发提示，用 coms_await / coms_get 取回答。1598 行，订阅 session_start、agent_end、session_shutdown，注册 4 个工具、1 个命令、5 个命令行参数。第 16 篇把“循环外的结果”送回自己；这一篇把另一个 Pi 进程的提示送进来，再在 agent_end 把回答送回去。
运行：just local-coms --cname dev（同时加载 minimal 和 theme-cycler；开两个终端各起一个）

    ① 四层结构

    第 1–6 步是启动链：命令行参数、socket、注册表。第 7–17 步是一次往返：A 的工具阶段（L1）→ A 的扩展写 socket（L3）→ B 的 socket 回调（L3）→ B 的 sendMessage（L2）→ B 的双循环（L1）→ B 的 agent_end（L2/L3）→ A 的 socket 回调唤醒 A 的 coms_await（L1）。

    0 / 17
    按“下一步”开始。第 1–6 步在循环外；第 7 步起是 A 问、B 答的一次往返，跨两个进程。

    ② 提示词上下文

    coms 不改系统提示词，但让别的进程往自己的上下文里写东西。B 收到的提示以 custom 消息进入 B 的上下文，开头带一行 [from A @ /path]，此外和用户消息没有区别：B 会照着做，用的是 B 自己的全部工具。B 的回答不是专门写给 A 的，而是 agent_end 时分支上最后一条 assistant 消息的文字。A 那边，回答作为 coms_await 的工具结果进入 A 的上下文。

    Bug：coms_await 按 Esc 停不下来，最长等 30 分钟。第 1434 行的 execute(_callId, params) 根本没接 signal 参数，Promise.race 里只有回答和超时（默认 PI_COMS_TIMEOUT_MS = 30 分钟）。和第 13–15 篇一样，Pi 的工具阶段就是 await tool.execute（agent-loop.ts:842），对方进程挂了或忘了回答，A 只能干等到超时。修法：把 signal 加进 race，abort 时立即返回。
    Pi 的命令行解析不知道扩展参数的类型。CLI 解析发生在扩展加载之前，args.ts:249–261 对不认识的 --xxx 一律“如果下一个参数不以 - 开头，就当成它的值”。于是 pi -e coms.ts --explicit "fix the login bug" 里，“fix the login bug” 被当成 --explicit 的值吃掉；之后 agent-session-services.ts:108 发现它是布尔参数，直接设成 true，那段文字就丢了，不会作为初始提问。布尔参数要写成 --explicit=true，或者放在最后。这是 Pi 的行为，不是本扩展写错；本扩展用 --cname 而不是 --name（第 537 行的说明），也是为了避开 Pi 自己的参数。模拟器下半部分可以试。
    本扩展正确处理了会话结束。和第 16 篇对比：这里订阅了 session_shutdown（第 1595 行），在 Pi 让旧扩展失效之前关掉 socket、删掉注册文件、停掉定时器，所以 /reload 之后不会留下孤儿。另外它还在 process 上注册了 SIGINT / SIGTERM 处理（第 1596–1597 行）：每次 /reload 工厂重跑都会再加一对监听，旧闭包也因此不会被回收（推断：/reload 十几次后 Node 会给出 MaxListeners 警告）。
    信任边界和 hops。入站提示进的是 B 的主对话，B 用自己的全部工具（包括 bash）执行它，能和 B 对话的是“同一用户下任何能写这个 socket 的进程”。第 813 行把 ~/.pi/coms 设成 0700，挡住了其他用户，但没有更细的鉴权。hops 用来防止 A↔B 无限互发（≥ 5 就 nack），它取的是“当前入站”的 hops + 1（第 1288 行）；B 的用户自己发起的 coms_send，如果恰好有入站还没回复，也会继承那条入站的 hops。response_schema 要求回答能直接 JSON.parse（第 1504 行），模型习惯把 JSON 包在 ```json 代码块里，会被判为 “response not valid JSON”。

    小结

    coms 把第 16 篇“从循环外送消息进来”的手法推广到了进程之间：socket 回调在循环外收信，sendMessage + triggerTurn 让接收方的外循环转起来，agent_end 把这一轮的最后一句话写回发送方，发送方的 coms_await 在工具阶段等着它。难点都在“这一轮回答的是谁的问题”：agent_end 只知道一个 run 结束了，不知道 run 里处理了哪些请求。下一篇 coms-net.ts 把同样的协议搬到 HTTP/SSE 上，让不同机器上的 Pi 也能互相发消息。
