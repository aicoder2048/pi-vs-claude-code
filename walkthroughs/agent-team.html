agent-team.ts

把主 agent 变成只会派活的调度员：工具只剩 dispatch_agent，系统提示词整个换成“你是调度员，下面是你的团队”。每次派活都另起一个 pi 子进程（JSON 模式），子 agent 有自己的工具和会话文件，编辑器上方用网格实时显示每个成员的状态。734 行，订阅 session_start、before_agent_start，注册 1 个工具、3 个命令。这一篇第一次出现嵌套的双循环：主进程的工具阶段里，跑着另一个进程完整的 settle。
运行：just ext-agent-team（同时加载 theme-cycler）

源码

点任意一行，看它属于哪一层、做什么。主体是三块：第 301–465 行 dispatchAgent 起子进程并解析它的事件流；第 469–561 行把它包成工具；第 631–733 行在 before_agent_start 和 session_start 里把主 agent 锁成调度员。

    ① 四层结构

    第 1–6 步是启动链：把主 agent 锁成调度员。第 7–16 步是一次派活：从主进程的工具阶段出发，经 L3 的 dispatchAgent 起一个新的 pi 进程（它自己就是一整套 L1–L4），再把子进程的事件流一路翻译回 L4 的网格。

    按“下一步”开始。第 1–6 步在循环外；第 7 步起是主进程 run 内循环里的一次派活。

    ② 提示词上下文

    agent-team 有两个上下文。主进程：setActiveTools(["dispatch_agent"]) 把工具声明缩成一个（安装），before_agent_start 返回一个全新的 systemPrompt（控制），而且没有接在 event.systemPrompt 后面，Pi 默认提示词里的项目上下文、skills、别的扩展加的内容都被换掉。子进程：Pi 默认提示词 + --append-system-prompt 的成员正文，任务作为 user 消息，上下文存在 .pi/agent-sessions/名字.json 里，跨派活累积。两个上下文之间只靠工具结果的文字连接。

    东西哪个进程段寿命
    调度员提示词主控制（强制提示词）每次 settle 重新生成；不落盘
    只剩 dispatch_agent主安装（工具清单）记进主会话；/reload 时 session_start 再设一次
    成员正文子安装（追加的系统提示词）每次派活通过命令行传
    成员上下文子子会话文件跨派活累积；主进程 session_start 全删
    派活结果主toolResult落盘，之后每个 turn 都在主上下文里

    Bug：按 Esc 停不下子进程，主 agent 也跟着干等。execute 的第三个参数是本 run 的 AbortSignal（tool-definition-wrapper.ts:22 原样转进来），第 478 行把它命名为 _signal 丢掉了，dispatchAgent 里也没有 proc.kill()。Pi 的 executePreparedToolCall 就是 await tool.execute(…)（agent-loop.ts:842），没有和 signal 赛跑，所以用户按 Esc 之后，主 agent 要一直等到子进程自己跑完才会收尾；子进程那边照常调用模型、改文件、花钱。修法：signal?.addEventListener("abort", () => proc.kill("SIGTERM"), { once: true })，并在 close 里区分被中止的情况。场景 B 演示了这段等待。
    Bug：上下文百分比超过 100 时，页脚和网格都会抛异常。页脚第 721–722 行和第 01 篇 minimal 一模一样：Math.round(pct / 10) 没有上限，pct ≥ 105 时 "-".repeat(负数) 抛 RangeError。网格卡片第 227–228 行同样没夹住（超过 100% 就出错），而它的分母是主进程启动时模型的窗口（第 678 行），用户中途换了更小窗口的模型时更容易超。修法同第 01 篇：Math.min(10, Math.max(0, …))。
    和本仓库的 agent 配置一起用时的两个坑。一是 teams.yaml 里的 pi-pi 团队，成员定义放在 .pi/agents/pi-pi/ 子目录里，而 scanAgentDirs（第 107–133 行）只扫一层，所以选这个团队会得到 0 个成员：网格显示 “No agents found”，调度员提示词里的成员目录是空的。二是 bowser.md 没写 tools，第 98 行默认给 read,grep,find,ls，这个靠 Playwright 命令行干活的成员拿不到 bash。模拟器里选 pi-pi 或 frontend 团队就能看到。这些不是扩展本身写错，是默认值和配置文件对不上。
    系统提示词是整个替换，不是追加。第 640 行没有用 event.systemPrompt，所以第 10、11 篇那种“接力”在这里断了：排在前面的扩展加的东西被丢掉，Pi 默认提示词里的项目上下文和 skills 列表也没了。对调度员来说大多用不上，但如果和 purpose-gate 一起装，目的只有在 purpose-gate 排在后面时才会保留。
    子会话在每次 session_start 时全部删除。第 680–688 行删掉 .pi/agent-sessions/*.json，注释说是为了“让子 agent 从头开始”。代价是 /reload、/new、/resume 都会让所有成员失忆，而主会话的历史里还留着它们以前的结果。这个目录是按 cwd 定的，同一项目里开两个 Pi 时，一个启动会删掉另一个正在用的子会话。
    和其他扩展叠加。setActiveTools(["dispatch_agent"]) 会停用别的扩展注册的工具。和第 12 篇 tilldone 一起装时会卡死：tilldone 工具被停用，模型建不了任务，而 tilldone 的 tool_call 门又会拦下 dispatch_agent（推断，从两边的代码推出）。另外网格每秒重装一次 widget（第 333–336 行的定时器调 updateWidget → setWidget），只需 requestRender 就够了。

    小结

    agent-team 用三个挂点把主 agent 变成调度员：setActiveTools 收走工具，before_agent_start 换掉提示词，dispatch_agent 工具在 run 内循环的工具阶段起一个子 pi 进程。子进程有自己完整的双循环和会话，主进程只在一个 await 里等它，再把它的事件流翻译成网格。下一篇 agent-chain.ts 同样起子进程，但把成员排成固定的流水线，上一步的输出直接当下一步的输入。
