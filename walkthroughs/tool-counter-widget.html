    ① 四层结构

    从 pi -e 启动到 widget 出现是前 8 步（循环外）；第 9–15 步是一次工具调用从 L1 冒到 L3 再落到 L4 的路径，每个工具都会走一遍。

    0 / 15
    按“下一步”开始。第 1–8 步在双循环启动之前；第 9–15 步在 run 内循环里，每执行完一个工具走一遍。

    ② 提示词上下文

    tool-counter-widget 不在安装、控制、装配任何一段：它不写提示词，也不读上下文。它从事件流旁路取数：tool_execution_end 先发出，紧接着才生成那条 toolResult 消息（agent-loop.ts:579 → 580）。所以它数的是“发生过几次工具执行”，而不是“上下文里有几条 toolResult”。

    入口循环本扩展改了什么会不会写回历史
    input / before_agent_start外不订阅：用户原文和系统提示词与不装时相同–
    context / message_end内不订阅：请求和落盘的消息逐字节相同–
    tool_execution_end内 每个工具只读事件的 toolName，返回值被忽略（这个事件也没有可返回的修改项）不会：计数只在闭包里
    toolResult 消息内不碰。被拦截或出错的调用同样会产生 toolResult（isError），所以“计数”和“LLM 看到的工具结果条数”是对得上的照常落盘（Pi 自己做）

    文件头注释和实现对不上。第 5 行写的格式是 Tools (N): [Bash 3] [Read 7] [Write 2]，实际输出没有方括号：每项是 " name count " 加一块背景色；工具名也不是首字母大写，而是 Pi 内置工具的原名 bash、read、write（例如 tools/bash.ts:418）。另外第 11 行 import 了 Box 但没用到。模拟器里显示的就是实际格式。修法：把注释改成 Tools (N): bash 3 read 7 （色块），删掉 Box。
    叠加拦截类扩展时，被拦下的调用也算一次。tool_execution_end 不只在工具真正跑完时发：tool_call 被拦截（beforeToolCall 返回 block）、工具不存在、参数校验失败、中途 abort，都会走 kind: "immediate" 分支，同样发一次 tool_execution_end，只是 isError: true（prepareToolCall，agent-loop.ts:718）。本扩展不看 isError，所以和 damage-control 一起用时，被拦下的 bash 也会让计数 +1。这不算写错：它数的是“调用尝试”。想只数成功的，在 handler 开头加 if (event.isError) return;。模拟器里勾选“被拦截 / 出错”再点按钮就能看到。
    widget 槽和页脚槽不一样。上一篇讲过，页脚只有一个槽，多个 setFooter 是最后一个赢。widget 是按 key 存的 Map：key 不同就并排叠放（按插入顺序从上往下），key 相同才替换（interactive-mode.ts:2412）。在终端里，widget 区（widgetContainerAbove）排在 Working 指示器之下、编辑器之上（interactive-mode.ts:984）。purpose-gate 要等用户在弹窗里填完目的才调 setWidget，所以它总排在本扩展下面，跟 -e 顺序无关。

    小结

    tool-counter-widget 是“事件写、渲染读”：在 run 内循环里订阅 tool_execution_end 改闭包里的计数，在循环外用 setWidget 挂一个组件，每帧重绘时读这些计数。它不刷新屏幕，靠 Pi “先发给扩展、再通知 UI”的顺序让下一帧看到新值。下一篇 tool-counter.ts，把同样的计数搬进页脚，并第一次用到 footerData（git 分支等）。
