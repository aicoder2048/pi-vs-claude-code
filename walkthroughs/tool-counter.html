tool-counter.ts

用一个两行的自定义页脚顶替内置页脚：第一行是模型、上下文条、token 和成本，第二行是目录、git 分支和工具计数。102 行，订阅 session_start 和 tool_execution_end，另外在页脚工厂里订阅了 footerData.onBranchChange。前三篇的数据各只有一个来源，这一篇的页脚同时读四个：事件流、会话树、上下文估算和 git HEAD。
运行：just ext-tool-counter

    ① 四层结构

    第 1–9 步是启动链（循环外），到页脚装好、git 监听登记完为止。后面是三条运行链：第 10–14 步是一次工具调用写计数，第 15–19 步是一条 assistant 消息落盘后页脚去读它，第 20–21 步是 git 分支变化。

    ② 提示词上下文

    tool-counter 不在安装、控制、装配任何一段：不写提示词，不改消息。但它的四个数据来源离上下文的远近不同，这是本篇要看清的地方。只有上下文条读的是“装配出来的上下文有多大”；token 和成本读的是会话树上的原始记录，compaction 之前的也算；工具计数和 git 分支跟上下文毫无关系。

    页脚上的数来源和上下文的关系compaction 之后/reload、/resume 之后
    上下文条、%ctx.getContextUsage() → agent-session.ts:4297估算装配后的上下文（最后一条 assistant 的 usage + 之后的估算）percent 为 null，显示 0%、条留 1 格（第 55 行的 || 1）从会话重算，不受影响
    in / out / $getBranch() 里每条 assistant 的 usage不是上下文：是根到当前叶子路径上所有请求的账单，压缩掉的部分也算不变（旧消息还在会话树上）从会话重算：/resume 后显示旧会话的累计
    工具计数闭包 counts无关：事件旁路，不落盘不变归零，显示 “waiting for tools”
    目录、(分支)ctx.cwd、footerData.getGitBranch()无关：读文件系统不变重新读 HEAD

    和 minimal 同一个 bug：percent ≥ 105 时 render 抛异常。第 55–56 行照搬了 minimal 的写法，getContextUsage 不把百分比限制在 100 以内，于是 "-".repeat(10 - 11) 抛 RangeError（第 63 行还会再 repeat 一次）。上下文溢出、正需要看页脚的时候，页脚反而画不出来。模拟器里把上下文 % 拖到 105 就能复现。修法：const filled = Math.min(10, Math.max(1, Math.round(pct / 10)));，勾上“修复越界”看效果。
    第 35 行的注释写错了。它说第 1 行是 “cwd + branch (left), tokens + cost (right)”，实际第 1 行左边是模型和上下文条（第 52 行的注释才是对的），cwd 和分支在第 2 行。像是改布局时漏改的旧注释。修法：删掉第 35 行，保留第 52 行。
    “in” 不含缓存，“$” 含缓存。第 42 行只加 usage.input，而 pi-ai 的 Usage 把缓存读写单独放在 cacheRead / cacheWrite（ai/src/types.ts:459）；第 44 行的 cost.total 却包含了缓存的费用。开着 prompt caching 时，页脚会出现“in 很小、$ 不小”的组合。内置页脚把 R（cacheRead）和 W（cacheWrite）单独列出来（footer.ts:183）。这是取舍不是错：本扩展想要的是简洁。模拟器里点“命中缓存的回复”再切到内置页脚对照。
    只算当前分支，不算整棵树。本扩展用 getBranch()：只数根到当前叶子的那条路。内置页脚用 getEntries() 数所有条目，还加上 compaction、branch_summary 的摘要请求费用（footer.ts:124）。所以 /tree 回到早先的节点后，本扩展的 $ 会变小，而钱其实已经花了。两种都说得通：一个是“这条对话的成本”，一个是“这个会话文件的总账单”。另外内置页脚按 leafId 和条目数缓存统计结果（footer.ts:102 getSessionStats），本扩展每帧从头遍历；会话很长时，流式输出期间每帧都要走一遍整条分支。
    两行的寿命不一样。第 1 行全部从会话和运行时现算，第 2 行的工具计数活在闭包里。/resume 一个旧会话时，第 1 行立刻显示旧会话的累计 token 和成本，第 2 行却是 “waiting for tools”。这不是 bug，但读者容易以为两行说的是同一段时间。场景 B 演示了这个错位。
    onBranchChange 这一行其实可以不写。Pi 自己在 interactive-mode.ts:1115 已经订阅了同一个 provider 的分支变化并 requestRender()，所以 HEAD 一变，即使扩展不订阅，下一帧也会重画。扩展再订阅一次只是多排一次重绘（requestRender 会合并，见 tui.ts:1033），无害。它的价值是示范“工厂里订阅、dispose 里退订”的写法：页脚被替换或 /reload 时 Pi 会调 dispose（interactive-mode.ts:2531），回调不会泄漏。另外别把两个 “branch” 搞混：getBranch() 是会话树上的路径，getGitBranch() / onBranchChange 是 git 分支。
    和其他页脚扩展叠加：最后一个 setFooter 赢。第 02 篇讲过，页脚只有一个槽，setExtensionFooter 每次都先清空容器（interactive-mode.ts:2534）。和 minimal、pure-focus 一起装时只会剩一个，被替换掉的那个会收到 dispose。这不是本扩展写错，是槽位的设计；想和别人共存应该改用 widget 或 setStatus。

    小结

    tool-counter 把第 01 篇的页脚和第 03 篇的计数合在一起，并多接了两个来源：render 每帧去会话树里数 assistant 的 usage，git 分支由 footerData 提供、HEAD 变了会通知。只有工具计数是事件写进来的，其余都是 render 自己现读，所以“刷新时机”取决于数据什么时候落盘，而不是订阅了什么。下一篇 damage-control.ts，第一次在 tool_call 上返回 block，从“看”变成“拦”。
