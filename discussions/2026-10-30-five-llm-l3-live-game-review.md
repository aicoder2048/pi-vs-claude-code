# five-llm 实战复盘：L3 如何以 pstack 式结构提供技能与服务

## 1. 证据与范围

读取了本机最新结束的实战棋谱：

```text
~/Library/Application Support/Five LLM/records/
8f4241b8-b7c7-470a-a6e1-dbc09772264f.json
```

- 保存时间：`2026-10-30T19:59:23.239Z`。
- 你执黑；模型执白：`openai-codex/gpt-6.1-sol`。
- 共 40 手；白方第 40 手 M9 连五获胜，终局原因 `five`，不是超时。
- 这是三局两胜的第 1 盘，比分为人类 0 : 1 模型；整场尚未结束。
- 20 个模型落子均有 `gomoku-knowledge/v1` 决策记录。

**重要边界：磁盘上是棋谱与决策摘要，不是完整运行日志。** `GameState.logs` 只保留内存中最近 80 条，`GameService.record()` 不导出 logs；Pi 使用内存 Session 并在回合结束后 dispose。因此不能从这份文件恢复全部工具调用次数、错误、重试、token 消耗、原始提示词或所有试算分支。

本次对完整棋谱逐手执行当前规则引擎重放：40 份逐手评估与保存值一致；20 份最终候选验证与保存值一致。这支持代码与这局棋谱的计算一致性，不是独立算法对棋力的证明。

pstack 对应关系以此前两份 Grok 分析为参考，并非此次重新核验上游插件实现。

## 2. 这局实际使用了什么

| 项目 | 观察结果 |
|---|---|
| 开局剧本 | 4 回合：总第 2、4、6、8 手 |
| 中盘剧本 | 13 回合 |
| 战术收束剧本 | 3 回合：第 24、36、40 手 |
| 时间紧迫剧本 | 0 回合；模型终局尚余约 390 秒基本用时 |
| observe 证据 | 20 回合保存的最后一次观察均为 `evaluate_threats` |
| 变化试算 | 15 回合记录了成功试算，5 回合记为 skipped；不是「总共仅 15 次工具调用」 |
| 保存的试算长度 | 3 回合最后保存的是 1 手试算，其余 12 回合包含对手回应 |
| 提交前自动验证 | 20 回合均有 `one-ply-only` 最终候选验证，均合法、warnings 为空 |
| 额外知识全文 | 所有 knowledgeRead 都只有入口与选中剧本，没有额外原则或三项技能全文读取的记录 |
| 最终候选排序 | 15 手选择启发式第 1 名；5 手选择第 2、6、8 或 9 名，未被强制替换为榜首 |

注意：`observed` 和 `simulated` 都是覆盖式变量。不能据此断言没有调用过 analyze_position，也不能恢复每回合所有试算。knowledgeRead 是去重列表，不能据此统计重复读取入口/剧本的次数。

### 三个有代表性的决策

**第 24 手 L8：战术事实驱动防守。**

重放到第 23 手后，白方无立即胜点，黑方唯一立即胜点为 L8。启动时选中 `endgame`，模型获取 evaluate_threats，跳过可选试算，落 L8。最终验证确认黑方不再有一手成五点。第 36 手 K7 是同样的模式。

**第 38 手 J6：候选与试算支持进攻判断。**

落子前双方都没有立即胜点，所以路由仍是 midgame。模型最后保存的试算是 `simulate_moves J6`。重放验证：此子形成 I5–J6–K7–L8 的斜向四子，白方下一手可在 H4 或 M9 成五；黑方此时无立即取胜点。模型公开理由中的两个成五端点与复算一致。

这也说明 endgame 的实现含义是「当前已有一手成五点」，不是泛指棋局进入收官；能创造决定性威胁的局面仍可能归 midgame。

**第 40 手 M9：直接获胜优先。**

黑方第 39 手占 H4，白方剩余的直接胜点为 M9。模型切入 endgame，取证后直接提交，不再做多余试算。连五为 I5–J6–K7–L8–M9；规则代码确认 winner=2。

以上是结构化信号与行动相符的实例；没有对照组，不能把胜局因果归于知识包。

## 3. 现在的 L3：不是一堆 Markdown，而是三个协作部分

### A. 知识/流程：告诉模型何时、为何、怎样用能力

位置：[`src/business/knowledge/`](../apps/five-llm/src/business/knowledge/)。

- **编排入口** `gomoku-coach`：将一手决策拆为 observe → compare → verify → commit。
- **5 条原则**：自由五子棋规则、证据优先、即时战术优先、时间预算、一次提交。
- **4 类剧本**：opening、midgame、endgame、time-pressure；不同情形采用不同探索强度与操作要求。
- **3 项技能**：evaluate-threats、check-legality、verify-board；说明适用情形、工具用法、证据和判断边界。

[`decision.ts`](../apps/five-llm/src/business/decision.ts) 的索引给每个条目一个稳定 ID 与用途描述。它目前是轻量的能力目录，不是带完整输入/输出类型和依赖关系的技能注册中心。

### B. 决策信号：把知识落到当前局面的可计算事实

`positionSignals()` 将输出明确分组：

| 信号类型 | 例子 | 推理中的用途 |
|---|---|---|
| 规则身份 | free-gomoku/v1 | 不误用 Renju 禁手；双三、双四、长连不是非法棋步 |
| 全盘一步事实 | immediateWins / opponentImmediateWins | 区分现在能赢、现在必须防守与常规布局 |
| 优先级 | win-now / answer-immediate-threat / develop | 指导注意力与决策顺序，不让候选分数遮盖立即胜负 |
| 局部启发式 | attack、defense、score、tags、前 12 个候选 | 缩小比较空间，但不是胜率或强制获胜证明 |
| 局限声明 | 局部剪枝、窗口棋形、不是深层证明 | 防止模型把弱信号解释成强结论 |
| 时间投影 | untilPeriodLossMs / untilForfeitMs | 区分丢一次读秒与本局判负，决定是否压缩探索 |

`turnGuidance()` 用这些信号做确定性路由：终局不启动；时间紧迫优先使用时间剧本；否则有即时战术使用 endgame；其余按前八手/其后选择 opening/midgame。时间剧本仍遵守先取自身立即胜、再处理对手立即胜的原则。

### C. 确定性服务：负责计算与执行，不把裁判权交给 LLM

| 服务 | 执行位置 | 模型触达方式 |
|---|---|---|
| 合法性、重放、胜负 | rules.ts | 分析、试算、验证、最终提交 |
| 棋形与候选评估 | tactics.ts | analyze_position / evaluate_threats |
| 副本上的交替变化 | play + analyze | simulate_moves，最多 6 手，不修改真棋盘 |
| 候选一步验证 | validateCandidate | validate_move，或 place_stone 自动执行 |
| 领域知识读取 | knowledge-loader.ts | read_knowledge，仅内置 ID，不是任意文件路径 |
| 回合、版本、计时、一次提交、比赛结算 | GameService + clock.ts | TurnPort.commit，由 place_stone 调用 |

这里的 distinction 是：**技能是使用能力的方法；工具是能力的受限接口；业务服务是计算与状态执行的权威实现。** 三者不是同一件事，也不必一一对应。

## 4. 与 pstack 的对应和差异

| pstack 分析中的模式 | five-llm 的对应物 | 当前差异 |
|---|---|---|
| poteto-mode 编排入口 | gomoku-coach + turnGuidance | 路由主要由代码选定，不是 LLM 自主选择任意 playbook |
| 原则索引 | 5 条 principle-* 的简短索引常驻上下文 | 完整原则文档按需读取，本局未见额外全文加载 |
| 任务剧本 | 4 个棋局情景剧本 | 都使用相同的四步 ID，不是一般任务的可变依赖图 |
| 专项技能 | 3 项领域技能说明 | 本局证明相关工具/验证运行，未证明技能全文读取 |
| prove it works | 提交前候选验证、重放与一手反击扫描 | 验证范围仅一步，不是完整棋力审查 |
| 共享 todo / 决策 artifact | 内存回合状态 + notes[].decision | 主要是成功提交时生成的摘要，不是实时持久化的待办日志 |
| subagents / 多模型 review | 尚未实现 | 当前只有主棋手；确定性扫描不能叫多模型审查 |
| 模型角色配置 | 单一当前模型与固定预算 | 没有独立 reviewer/judge 角色 |

尤其要避免误解：`PiDriver` 仍设置 `noSkills: true`。我们没有开启 Pi 的通用技能发现，也没有安装 pstack 插件。

实际加载链路是：

```text
GameState 棋谱/时钟快照
  → turnGuidance：信号与剧本路由
  → knowledgeContext：入口全文 + 原则/能力索引 + 当前剧本全文
  → PiDriver：显式上下文注入
  → 主模型：取证、可选读技能、可选试算
  → gomoku 扩展：证据门禁 + 最终候选验证
  → TurnPort.commit / GameService：权威提交与结算
  → notes[].decision：决策证据摘要 → Electron 原子保存
```

所以准确定位是：**一个 pstack-inspired、宿主显式管理的领域知识包与工具服务层，而不是完整的 pstack 式多 Agent 技能平台。**

## 5. 本局揭示的不足

### 5.1 技能「可用」不等于实际被读取或遵循

knowledgeRead 的入口与剧本是扩展初始化时登记的，与宿主注入路径相对应，不是模型主动调用 read_knowledge 的证据。其余技能全文没有出现在记录中。入口与剧本已覆盖本局主要步骤，可能因此无需再读全文，也可能说明技能描述与触发条件不够突出；单局无法区分。

### 5.2 compare=done 的含义偏弱

它只表示本回合成功执行过至少一次 simulate_moves：

- 第 22、34、38 手最后保存的试算只有 1 手，未包含对手应手。
- 第 12、14、28、34 手最后保存的试算首着不是最终落子。
- 第 12、28 手最终落子出现在试算的第三着，不等于验证「现在立刻下该点」的相同局面。

不能据此断言这些回合从未验证最终候选，因为更早分支已被覆盖；但也不能用目前的 compare=done 声称已比较多个候选及其最强反击。最终自动验证仍针对真实最终候选执行，只是范围为一步。

### 5.3 自动验证不等于模型在行动前获得反馈

`place_stone` 在提交前计算 validation，但策略 warnings 不阻止提交。若模型没有先调用 validate_move，则自动检查即使有警告，也会随 accepted:true 返回并结束回合，模型没有在这次提交前根据该警告修正的机会。

本局所有最终 warnings 均为空，未触发这一缺口。需要区分：执行了检查、记录了证据、模型看见反馈、模型据此修正，是四种不同保证。

### 5.4 进度不是完整的持久化状态机

observe/compare/verify/commit 的记录在成功提交时统一生成；失败、取消、超时且未落子的回合不会出现在 notes 中。skipped 原因也主要来自固定模板，不是逐步记录的实际预算决策。不能把这当作已经实现完整的 pstack todo 耦合机制。

### 5.5 无法评价未走到的分支

本局未使用时间剧本，没有额外技能加载记录，也没有足够证据统计失败纠错。胜局不能证明这些分支都可靠，更不能证明相对旧版有棋力提升。

## 6. 建议的下一轮优先级（本次未实现）

1. **先补可观测性，不急着加 subagent**：记录 attemptId、gameId、revision、路由原因、注入条目/内容版本，以及工具开始/结束、结构化参数/结果、错误、耗时和最终状态。失败回合也持久化；不记录密钥与私有思维链。
2. **证据绑定候选**：保留 simulationId、基准 revision、完整分支序列、起始候选、应手数量、结果与限制。区别「探索过别的候选」「验证了最终候选」「包含对手回应」。
3. **区分 knowledge injected / fetched / applied**：前两者可以直接记录，applied 需用公开结构化决策或行为断言验证，不能从注入成功推断。
4. **让关键警告进入行动前反馈**：优先使用现有 validate_move；必要时将有风险的提交设计为 needs_review，再由显式确认/覆盖完成，而不是把策略建议伪装成非法规则。
5. **建立情景评测**：唯一防守、多威胁、直接取胜、危险候选、读秒、非法纠错等；再对比「仅工具」「入口+原则」「完整剧本/技能」的遵循率、失误率、耗时和成本。

## 总结

本局已经证明知识包不是静态文档摆设：主模型获得情景化上下文，调用领域计算服务，按战术信号切换决策方式，并通过权威提交服务落子、保存证据。

但目前最强的实战证据集中在 **入口/剧本编排 + 结构化战术信号 + 受控工具服务**。专项技能按需读取、候选级比较证据、行动前审查反馈与失败回合审计还不充分。下一步最值得强化的是「技能适用条件 → 服务调用 → 候选证据 → 判断 → 执行」的可追踪契约，而非单纯增加 Markdown 数量。
