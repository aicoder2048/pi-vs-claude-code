# 讨论记录：边牧任务桌面主界面（左侧）改进

- **日期**：2026-11-01
- **参与**：Sean、Claude
- **状态**：仅讨论，未实施。后续跟进时先细化为规格。
- **范围**：`apps/tilldone/` 桌面端的主界面（左侧对话区），兼及右侧任务面板与底栏。

---

## 1. 问题

Sean 在 mini-six-ren 上用 `just tilldone-with-pstack` 跑"改进桌面版三传 AI 解读"时的观察：

- **左侧空间浪费。** 大部分时候是一串折叠的工具调用，每行只有"read · 已完成"，信息量几乎为零。
- **右侧不透明。** 任务粒度有时较粗，或者交给了子 agent。等待时间长、信息少，只剩一个红点在亮。

同一天的实际情况印证了这一点：

- 一次并行子 agent 调用等了 24 分钟。其中两个审查一分钟左右就结束了，剩下的浏览器验收子 agent 层层转包，嵌套了约 4 层，各层都在空等。界面上完全看不出来。
- 一个 pstack 子 agent 被显式指定为 `anthropic/claude-sonnet-5-5`，走了按量计费的 API，花费约 $0.16，界面上也没有任何提示。之后已在 TillDone 扩展里加了计费拦截。

## 2. 方向

把主界面从"对话记录"改成"运行仪表盘"，回答三个问题：现在在干什么、为什么这么慢、还要多久。

## 3. 提议

### 3.1 实时活动与子 agent 可见（解决不透明）

数据其实已有：pstack 的 `subagent` 运行中会通过 `onUpdate` 持续推送 `details.results`，包含每个子 agent 的消息、轮数和 token 用量。桌面端目前没有呈现。

- **"正在进行"条：** 固定在左侧顶部，一行说清当前状态。例如"模型思考中 12 秒"、"执行 bash：`uv run python -m unittest…` 已 40 秒"、"等待 3 个子 agent"。
- **子 agent 树：** 挂在当前任务下。每个子 agent 显示角色、模型、已运行时长、轮数，以及最近一次工具调用或最近一句话。嵌套转包一眼可见。
- **距上次活动的时间：** 例如"最后动静：2 分钟前"，超过阈值变色。用来区分卡住和在干活，比预测时间更有用。

### 3.2 工具调用压缩成时间线（解决空间浪费）

- **合并连续调用：** 合成一行摘要并带关键参数。例如"读取 6 个文件：ai_agent.py、web.py…"、"运行测试：91 通过"。展开后再看单个调用。
- **突出重要内容：** 助手文字、失败的工具、改动的文件放大显示。成功的读文件弱化。
- **任务与时间线联动：** 点右侧某个任务，左侧只显示该任务期间的活动。现有的"模型/工具"计数可点击。

### 3.3 新增入口

Sean 提出前三项，后两项为补充。

1. **上下文检查器：** 抽屉或标签页，展示系统提示词、追加提示词、可用工具及描述、已加载的扩展和技能、`AGENTS.md`/`CLAUDE.md` 等上下文文件。每项标出 token 占比，例如能看出 pstack 技能文本占了多少。
2. **双循环状态：**
   - 内循环（Pi agent 循环）：第几轮，当前阶段是思考、执行工具还是等子 agent。
   - 外循环（TillDone 督促循环）：催促次数、剩余任务、下一次催促的条件。
   - Steering 队列与 follow-up 队列放在同一处。现在输入框上方的已排队消息可并入。
3. **上下文窗口用量：** 底栏进度条，例如"63k / 272k"，标出上次压缩时间，快满时提醒。
4. **变更面板：** 本次会话改了哪些文件、增删多少行，可点开看差异。直接回答"它动了我哪些东西"。
5. **额度与费用：** 按模型显示用量。Codex 订阅的计费是名义上的，主要看配额。出现按量计费模型时醒目标红。

### 3.4 时间：实际与预测

Sean 的需求：总用时（实际/预测）、单个任务用时（实际/预测）。

- **实际用时：** 总用时、每个任务、每个子 agent 都能精确显示，建议直接做。
- **预测：** 没有可靠来源。可行做法：
  - 按历史估算：同类任务的历史用时，或"剩余任务数 × 平均每任务用时"，给区间并明确标为估计。
  - 让模型在 `tilldone add` 时给出每个任务的预估。通常偏乐观，但可与实际对比，长期有校准价值。
- 建议先只做实际用时和"距上次活动"，积累历史数据后再加预测。

## 4. 建议顺序

1. 实时活动条加子 agent 树。痛点最大，数据现成。
2. 工具调用压缩成时间线，并与任务联动。
3. 上下文用量进度条，以及每个任务的用时。
4. 上下文检查器、双循环面板、变更面板。
5. 时间预测。

## 5. 待核实

- Pi 的 RPC 接口能否直接提供系统提示词全文、工具列表和上下文 token 数。拿不到的部分，只能由 TillDone 扩展在 Pi 进程内收集，再转发给桌面端。这决定第 3、4 步的工作量。
- `subagent` 的 `onUpdate` 推送在 RPC 事件里的具体形状（预计是 `tool_execution_update`），以及更新频率是否足够驱动实时树。
- 嵌套子 agent 不加载 TillDone 扩展，第二层以下的活动只能通过上层子 agent 的推送间接获得。
