## 1. 为什么红方能走第33手？黑方为什么被动？

这步合法：D5 到 F4 是横向两格、纵向一格，马腿 E5 为空；未暴露红帅，也不是将帅照面。它不是将军，却是**马双攻**：F4 红马可以合法吃到 G2、E6 两匹黑马。重放后双方均未被将军，黑方还有 **39 种合法应手**，不是困毙、将死或规则锁死。裁判不应禁止玩家的合法好棋。

被动的前因在黑方第32手 `黑马 G5 → E6 吃兵`。保存的公开计划看重吃中兵、马炮活动和红炮吃 G3 的交换，没有提到 F4 双攻。该手的独立审查记录为：

- `risk = no-direct-loss-found`、`estimatedNet = 0`；列出的反击是 `红炮 C3 → G3 吃卒`。
- 实际提交的多步复查完成4层、20000节点，`rootScope = requested-subset`、只搜这一个根候选，分数9；不是比较全部黑方选择，更不是安全证明。
- 第32手后保存的红方专家摘要只审查了12/51个候选，靠前的是吃子等走法；没有在摘要候选中揭示 F4 双攻。

因此可以确认：**已有有限审查/公开计划没有揭示这个安静双攻威胁**。不能从未保存的思考过程断言模型具体如何想错，也不能把局面被动解释为引擎不准黑方走棋。第33手后的 `黑车 I1 → C1` 等应手仍合法；浅搜分数不用于宣称黑方必胜/必败。

本次保留合法棋规，增加可移植的33手棋谱及双攻/39应手回归测试。棋力后续建议：在候选排序和对手威胁报告中加入安静双攻/多目标攻击，针对第32手做等预算候选比较；增加搜索覆盖不能代替正确处理未知，也不应硬禁有意弃子。

## 2. 实际停止链路

遥测记录如下，所有8个模型区间和8个工具区间均为 `ok`：

| 模型请求 | 工具 |
| --- | --- |
| 1 | read |
| 2 | analyze_position |
| 3 | read |
| 4 | search_position |
| 5 | review_move |
| 6 | read |
| 7 | read |
| 8 | update_plan |

分解：模型往返 **22658.049 ms**，工具 **373.543 ms**，预搜索 **379.063 ms**，提交复查 **0 ms**。没有调用 `move_piece` 或 `resign_game`，也没有落子审查拒绝形成的循环。

结合旧 `PiDriver.run()` 的代码，直接匹配的停止路径是：第8次请求仅更新计划 → Pi准备第9次请求 → `turn_start` 超过8次上限，宿主 `abort()` → 驱动抛出请求上限错误 → `GameService` 将回合置为 `error`，等待人工重试。第9次在发送前被中止，所以没有第9个网络区间。旧文件缺少具体错误文本，**请求上限是根据完整区间序列与对应代码定位的高置信根因，不冒充读到了原始错误日志**。

这也解释了截图为何显示“最近未落子尝试…8次”：不是正在无限思考，而是早已停止。

棋钟没有随着失败停下（比赛原有规则）。黑方本手累计约 **1539.500秒（25分39.5秒）**，而模型尝试只占23.476秒；余下约 **1516秒（25分16秒）**没有新的尝试记录，最后正常判棋钟耗尽。

由最终棋钟字段反推的近似 UTC 时间：

- 开始黑方第34手：2026-10-31 23:36:59；
- 请求失败：约23:37:23；
- 棋钟耗尽：2026-11-01 00:02:38.848。

时间为棋钟累计与区间计算，不是原始请求日志时间戳。

**没有证据支持网络Timeout、死循环或互斥锁死锁。** `error` 时原重试按钮可用；最终截图已是 `over`，此时重试按钮禁用是终局规则，并不证明此前被锁。核心缺陷是原生技能读取同样消耗续问次数，却没有最终提交预留；失败信息不显眼且被终局显示覆盖，让“停止等待重试”看起来像“机器仍在思考”。

## 后续预算调整：当前10次（8+2）

不能仅凭工具名相同，把后几次请求归类为语义重复或徒劳：第6、7次虽均为 `read`，旧记录没有读取路径、内容或模型对话，不能确认是否重读同一材料；第8次 `update_plan` 则是不同的工作流动作。这不证明每次调用都有价值，但不足以选择“已确认无意义重复”的10次分支。此前按用户的另一分支暂调为18次（16+2），未冒充已完成语义去重判断。最新要求改为 **10次（前8次分析，最后2次提交/纠错）**，同时增加[结构化调用证据](call-audit.md)，让未来可以基于路径/范围、候选/计划和返回指纹判断，而非只看工具名。

上面的8次停止链路是原始历史证据，保持不变。16次工具调用预算也不变，终局工具仍可在工具预算耗尽后使用；增加请求次数不保证模型会用满、变强或更快。

## 已落地修复

1. **预算有收尾阶段**：初次修复为8次（6+2），中间曾调为18次（16+2）；当前按最新要求改为10次（8+2）。前8次可分析/读技能/计划，最后2次只声明 `move_piece` / `resign_game`，可提交并纠正一次审查错误。初始提示明确说明。工具集在第8轮 `turn_end` 后切换；真实Pi测试确认第9、10个HTTP请求只声明终局工具（在 `turn_start` 切换会晚一轮，不能仅测内存状态）。驱动、日志分母和提示共用预算常量，避免只改执行上限而留下旧提示。
2. **失败可诊断**：`attempts[].error`、失败决策 `decision` 和有界 `logs[]` 随棋谱保存，保持 `chinese-chess/v1` 可选字段兼容；先记录失败信息再发出新的attempt保存键，避免只存到耗时。不会保存私有思维链或完整模型对话。
3. **失败回合撤权**：驱动返回错误后也abort该回合信号，拒绝遗留异步工具迟到落子；重试创建新信号，原棋钟继续，不退款、不加秒、不替换为本地AI。
4. **失败不是思考**：持续的警告明确写“机器请求已停止，尚未落子”“棋钟仍在运行”，高亮可用重试按钮；终局仍保留前面的失败原因，专家报告显示具体错误。

仍然可能遇到模型不提交、最终审查连续拒绝或真实网络挂起。本次不擅自添加固定90秒单步判负/自动认输，不无界自动重试，也不替模型选棋。后续若加入网络无进展看门狗，应作为可配置技术故障恢复（明确提示/有界重连），不改变比赛棋钟与合法长考规则。
