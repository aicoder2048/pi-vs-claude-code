# 弈境：计时与比赛规则

## 采用什么规则，以及参考什么

弈境仍是 **15 路自由五子棋**，不是带黑方禁手或指定开局的正式连珠赛事。不同棋类、赛事对用时、开局、和棋与赛制的规定不同，并不存在一个可以直接照搬的“所有五子棋国际比赛统一计时”。

本应用借鉴：

- [RIF《International Rules of Renju》](https://www.renju.net/rifrules/) §9.4：未在规定时间完成规定着数可判负；§14.1–14.5：双方独立棋钟、行棋后切换、以棋钟记录判定。这里只参考计时原则，不套用其禁手、开局或人工申诉规定。
- [Sensei's Library：Byo-Yomi / Japanese Overtime](https://senseis.xmp.net/?ByoYomi)：常见围棋基本用时加日式读秒；完整消耗一次读秒后次数减少，未用完的读秒部分在完成该手后恢复。

**10 分钟 + 3 × 60 秒、三局两胜是本应用的默认选择，不宣称是上述组织指定的统一赛制。**

## 一局的棋钟

双方各有一个独立棋钟，只有当前行棋方扣时。新局从黑方开始计时，合法落子在主进程收到并验证时生效，随后切换到另一方。不需要手动按钟。

“每局用时”指**每方在这一局累计的思考时间**，不是共享的整局墙钟截止时间。每个新局重置双方用时；整场多局比赛没有共享总时钟。

### 默认：基本用时 + 日式读秒

默认每方每局 **10 分钟基本用时 + 3 次、每次 60 秒读秒**。

| 情况 | 处理 |
|---|---|
| 还有基本用时 | 扣本方累计局时，没有独立的每步硬上限 |
| 基本用时用完 | 自动进入读秒，**不立刻判负** |
| 读秒内完成一手 | 本手剩余秒数恢复至 60 秒；已损失的次数不恢复 |
| 一次 60 秒用完，仍有其他读秒 | 扣一次机会，同一手进入下一次 60 秒；**不丢弃该手，也不替玩家落子** |
| 最后一次读秒用完 | 判该方**当前局负**，对手获一个胜场；不是直接输掉整场比赛 |

例：已经进入 `3 × 60 秒`，某手思考 75 秒，先扣掉一次读秒，余两次；此时成功落子，下次轮到自己仍是 `2 × 60 秒`。下一手只用 40 秒，仍保留两次。剩两次时一手连续用到 120 秒，则在最后一次耗尽时判负。

可以将基本用时设为 **0 分钟**，从第一手起就执行每步读秒。读秒设置范围：每次 5–300 秒，共 1–10 次。

### 可选：包干制

双方各有设定的基本用时（1–180 分钟），所有自己的回合累计扣除；对手行棋时停表。**自己的累计局时归零就判本局负**，没有额外读秒，也没有独立步时上限。

这与读秒超时不同：包干没有“丢一次读秒后还能继续”的缓冲。

### 超时边界与请求失败

- 恰好到达截止时刻视为超时；界面秒数向上取整，裁决使用毫秒，不凭屏幕文字判断。
- 棋钟由 Electron 主进程中的业务层维护，200ms 通知一次界面；落子提交、重试等操作还会主动核对截止时刻。即使定时器尚未触发，迟到落子也不能抢在超时前被接受。
- 定时器延迟不会只扣一次：一次延迟跨过多个读秒周期会补扣所有已耗周期；最后周期耗尽则结算一次，迟到的 LLM 工具请求被中止并拒绝。
- **LLM 网络请求、工具调用、失败重试和 API 排队均计入机器方用时。** 应用无法可靠区分“模型思考”和“网络等待”，不自动赠送时间。
- Pi 的单次 Agent 请求仍有 90 秒技术超时。这只是停止请求、显示错误，不直接判棋局负；业务棋钟继续运行，可重试，直到比赛用时真正耗尽。
- 取消的是模型请求，不是棋钟。回看、换模型、重试、打开设置/导出对话框、窗口失焦或最小化都不暂停、不重置用时。
- macOS 关闭窗口但未退出应用时也继续计时；系统休眠/长时间阻塞后，下次校验按经过的系统时间补扣。本地版本使用系统时间，不提供修改系统时间的反作弊保障。
- 主进程完全退出后不会恢复未完成比赛；当前版本没有跨启动续局。比赛中途退出或重新开始不等同于正式赛事仲裁或比赛成绩认证。

## 三局两胜 / 五局三胜

在「新比赛 / 设置」中选择：

- **三局两胜（默认）**：先拿到 2 个胜场者赢得比赛。
- **五局三胜**：先拿到 3 个胜场者赢得比赛。

比分属于**你 / LLM**，不属于黑棋 / 白棋。首局可选择自己的颜色，此后每个分出胜负的局交换黑白，黑棋先行。棋盘连五、对手包干超时、对手最后读秒耗尽、对手认输，均各计一个胜场。

双方填满棋盘但无人连五则和棋：不加胜场，保留本盘颜色，点击「和棋重赛」重开，双方时钟重置。因此“三局两胜”最多需要三局**分出胜负的棋局**，计入和棋后实际盘数可能超过三盘。五局三胜同理。这是本应用明确采用的重赛约定，并非所有国际赛事都如此处理和棋。

一局结束后时钟停止，保留棋盘供复盘。点击「下一局」才开始下一盘和计时；达到所需胜场后，不再允许加赛，只能另开比赛。认输只判当前局负，可能因对方刚好达到所需胜场而同时结束比赛。

## 悔棋与设置

正式式样的默认比赛**不允许悔棋**。可在新比赛设置中启用「允许练习悔棋」，界面会标记为练习模式：

- 悔棋撤销上一回合并重建棋盘，但不返还基本用时、已经失去的读秒次数或未用完的当前读秒。
- 已结算的棋局不能悔棋，避免重复修改比分。
- 比赛设置只能在创建新比赛时应用，不能中途增加时间或更改几局几胜；开启新比赛会清空比分并重新分配用时。

## 棋谱与界面

每盘仍有独立棋谱文件。JSON 的 `outcome` 保存胜方和终局原因，`clock` 保存时钟快照，`match` 保存比赛 ID、设置、累计比分和已完成各盘摘要。最后一盘的文件包含整场摘要；之前各盘的完整落子通过各自的 `gameId` 文件关联。超时/认输不伪造棋盘连五，`position.winner` 与业务层 `outcome` 分离。

桌面采用固定视口网格布局，棋盘依据剩余宽度和高度共同缩放。已自动验证 `1280×900`、`1100×760`、`1010×700` 窗口下棋盘、时钟、动作按钮、音乐与回看控件都在视口内，无需整页滚动。很长的模型理由、错误信息、棋谱列表和日志只在各自区域内部滚动。
